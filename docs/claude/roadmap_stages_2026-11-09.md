## 고정 원칙 (모든 단계)
- **운영 주체**: 사업자등록·통신판매업 신고·입찰·운영·CS의 '운영자'는 **운영사(대표·운영팀)**입니다.
- 사업 지위: **통신판매중개자로 시작**. 다만 지위는 선언이 아니라 **실제 역할**로 정해지므로, 기능을 추가할 때마다 아래 조건을 다시 확인합니다.
  - 상품이 누구 것인가(셀러 / commerce_ai), 주문을 누가 접수하는가, 대금을 누가 받는가, 청약철회·환불을 누가 처리하는가.
  - 셀러 상품 + 셀러가 대금 수령 = 중개자. commerce_ai가 대금을 먼저 받으면 결제대금 수령 중개자(제20조의3, 7단계 검토). 중개자가 청약 접수·대금 수령·배송 등 판매자 업무를 직접 하면 그 업무에 대한 책임이 따로 생김(전자상거래법 해당 조문 확인). 직접 매입 판매는 통신판매업자(보류).
  - GPT Instant Checkout·구글 UCP 체크아웃·Google Pay를 써도 OpenAI·구글은 판매자가 아님. AI 결제는 국내 미지원이라 지금은 쓰지 않음(UCP는 카탈로그 노출만).
  - **B2B 입찰 폐쇄몰은 예외로 따로 봄**: 낙찰해 기업·기관에 공급하면 운영사가 공급 계약 당사자(판매자). 1차는 발주처가 일괄 결제하는 사업자 간 거래(세금계산서)만, 임직원 개인 결제형은 7단계 자체 결제와 함께 검토.
  - 고객 화면에 **'장바구니'·'주문하기'처럼 여기서 사는 것으로 오해할 말을 쓰지 않음** — 보관은 '내 보관함', 구매는 '판매처에서 보기'(2026-11-18).
- 셀러 유형: 직접 재고 셀러 + **정식 위탁판매 셀러**(공급사와 위탁 계약, 공급사 직접 배송) 허용. **소매몰 차익거래(쿠팡·네이버에서 사서 되팔기)는 commerce_ai와 셀러 모두 불허**.
- 결제: **1단계는 셀러 쪽 결제**(스마트스토어·자사몰, commerce_ai는 대금을 받지 않음). **2단계 자체 결제**는 거래 규모를 본 뒤 국내 PG + 지급대행·파트너 정산으로 (법률 검토 후). Stripe는 한국 사업자 가입 불가.
- 수익: 쿠팡 파트너스 제휴 수수료 + **셀러 월 이용료(정기 구독)** + B2B 입찰 공급(폐쇄몰). 판매 수수료는 자체 결제를 연 뒤 재검토.
- 카테고리: **식품 우선**. 로드맵 완료 후 다음 카테고리 추천 (후보: 주방·조리도구 → 생활용품 → 화장품은 역직구와 함께).
- CS: **분야별 AI CS, 사람 관여 최소화**. 이용자별 창구 3개(고객·셀러 센터·B2B) 안에서 AI가 분야를 판단해 처리. 운영자(운영사)는 '사람이 반드시 맡는 일'(식품 안전, 법적 분쟁의 처리 방안, 개인정보 요구·유출, 셀러 입점 승인·정지·해지, 이용료 환불·예외, 계정 예외 복구, B2B 가격·납기 확정·제출, 위급 신호, AI 규칙 변경 승인·주간 검수)만 함. AI는 환불·보상·제재 면제·가격 확정을 하지 않음. 품절·입고 대기 상품 문의도 CS 채팅에서 처리(화면에 '품절 신고' 버튼은 두지 않음, 2026-11-17 결정).
- 알림: **카카오 알림톡은 정보성 알림 발송에만** 씀(주문·배송·선물 도착·마감·티켓 회신·보안·셀러 경고·운영자 긴급). 상담은 계속 자체 채팅(카카오톡 채널 1:1 채팅·네이버 톡톡 상담은 쓰지 않음). 할인·이벤트·트렌드 글 홍보는 알림톡으로 보내지 않음. 실패 시 문자 대체 발송. 휴대폰 번호는 알림에 동의한 경우만 받는 선택 항목.
- **별도 연구 흐름은 추천에 바로 합치지 않음**: 해외배송 last mile 증거 연구와 B4-B 배송 공급자 평가 연구의 결과는 추천 점수·순위나 자동 배정에 곧바로 넣지 않습니다. 넣으려면 별도 결정(권한)이 필요합니다.
- **베타 전 순위 동결**: 베타 전에는 새 순위 변경을 하지 않음. 클릭·구매 기록은 측정용이며 순위에 쓰지 않음(2026-11-16 결정, `claude/click_purchase_link_design_2026-11-16.md`). 고객 선호 조건(채식·맵기 등)도 베타 전에는 필터·표시에만.
- 페이지 스크래핑 금지, 제휴 여부는 순위에 반영하지 않음, 근거 없는 가격·품질 단정 금지, 모든 가격에 확인 시각. **에이전트 브라우저(Ego Lite·Playwright 등)는 우리 사이트 화면 시험에만** 쓰고 외부 쇼핑몰 데이터 수집에는 쓰지 않음(약관·봇 탐지·로그인 계정 차단 위험). 구글 트렌드는 공식 Trends API 승인 전에는 미연결(pytrends·대행 API 쓰지 않음).
- 쿠팡 판매처 링크는 모두 `/go` 경유(클릭 기록), 쇼핑커넥트 발급 링크만 예외(블로그 전용).
- 외부 API 수치(호출 제한·페이지 크기·처리 시간)는 **확정값이 아니라 검증 항목**. 실제 계정의 응답 헤더·권한으로 확인하고 측정값을 기록.
- 개인정보: 최소 정보 SSO, 데이터 흐름별 국외 이전 확인, 로컬 모델에도 접근 권한·로그 최소화 적용. 개인정보가 오가는 CS 분야는 로컬 모델에서만 처리. 주문자 정보를 공급사에 넘길 때는 셀러의 수탁자로서 위탁 계약·최소 항목·전송 기록·보존 후 파기. 폐쇄몰 임직원 명단은 발주처의 수탁자로서 같은 원칙(발주처별 분리 저장, 쿠폰사·공급사 재위탁은 발주처 동의). **알레르기 등 건강 정보는 받지 않음** — '피하고 싶은 재료'로만, 기기 안에만 저장.
- 커밋에 실제 키가 든 `.env`·백업 파일 포함 금지. 공개 저장소이므로 수익·금액은 커밋 문서에 쓰지 않음.
- **브랜치는 작게, 작업 폴더도 나눔**: 한 작업 창의 결과는 그 창을 마칠 때 PR로 main에 합칩니다. 여러 창이 한 브랜치·한 작업 폴더에 쌓지 않습니다(11-16 `stage1/relevance-r0` 50여 커밋, 11-18 `stage2/trend-posts`에 여러 창 커밋이 섞인 교훈). 창마다 `git worktree`로 폴더를 따로 둡니다.

- 흐름: 연결 → 가져오기 → AI 변환(OCR `commerce_ai_local_ocr`, 템플릿 재구성, 원본 유지 선택, 식품 필수 표시 누락 시 보완 요청) → 미니숍 `/shop/{업체}` → 셀러 확인·운영자 승인 → 구매는 스마트스토어 상품 페이지(외부 유입 셀러 수수료 0.91%) → 가격·재고 동기화 → 구조화 데이터 공개.
- **UCP 카탈로그 공개 — 두 가지를 따로 봅니다** (아래 'UCP 현황과 역할 구분' ③):
  - **자체 UCP 서버 간 연동**: 판매자(Business) 프로필·카탈로그를 우리 도메인에 게시하면 UCP를 지원하는 플랫폼·에이전트가 사양의 프로필·기능 협상으로 접근할 수 있습니다. Google 승인과 무관하지만, 판매 주체(Merchant of Record)·가격·고지 책임은 셀러 계약으로 먼저 정해야 합니다.

## 5단계 상세: 정식 위탁판매 셀러와 발주 자동화
- 입점 심사: 사업자등록, 통신판매업 신고, 공급처 증빙(위탁 계약서 또는 공급사 확인), 사진·상세 사용 허락, 식품이면 영업신고 확인. AI 1차 검토 → 운영자 최종 승인.
- 상품 등록 규칙: 출고지·반품지·예상 배송 기간 필수, 상품마다 공급사 연결 필수, 소매몰 출처 상품(같은 사진 감지 등) 차단.
- 입점 계약: 배송·반품·품절 책임과 기한은 셀러(공급사 사정이어도 고객 응대는 셀러). commerce_ai는 접수·추적·회신(3·10영업일). 주문자 정보 전달 조항.
- 운영 지표: 배송 지연률·품절 취소율·반품률·송장 등록 지연 → 기준 초과 시 노출 축소(자동) → 정지(운영자). 기준값은 베타 후 결정.
- 발주 자동화(주문자 정보 자동 입력): 1단계 결제 구조에서는 주문이 셀러 판매처에 있으므로 셀러가 허락한 주문 조회(커머스API 등)로 읽음 → 공급사별 발주서(엑셀 템플릿 우선, API는 공급사별 확인) → 처음엔 셀러가 "발주 보내기"로 확인 전송, 신뢰가 쌓이면 자동 전송 선택 → 송장 회수(API·엑셀 업로드) → 송장 등록·배송 조회 연결(셀러 판매처 송장 반영 가능 여부 확인) → 품절·지연 알림. SCM에 '발주·송장' 메뉴. commerce_ai는 셀러 대신 주문을 **접수·변경하지 않고** 전달만 함(지위 조건 유지).
- 개인정보: 공급사는 셀러 처리방침에 수탁자(또는 제공받는 자)로 기재, commerce_ai는 셀러의 수탁자로 위탁 계약, 필요한 항목만 전달, 전송 기록, 배송 완료 후 기간 경과 시 가림·파기. 구성은 법률 검토 필요.
- 시작 전 결정: 운영 지표 기준값, 공급사 발주서 형식·연동 방식(엑셀·API·메일), 주문 조회 권한 범위, 개인정보 수탁·제공 구성과 보존 기간.

## 5단계 상세: B2B 입찰 폐쇄몰 (2026-11-13 결정)
- 목적: 기업·기관 임직원 선물·기념품 입찰에 **폐쇄몰 운영을 포함해 제안**하고, 낙찰되면 발주처 전용몰로 수행. B2B 파이프라인(공고 분석 → 협력업체·소싱 → 제안서)의 마지막 '수행' 단계. 입찰·계약·운영 주체는 운영사.
- 지위: 운영사가 공급 계약 당사자. **1차는 기업 일괄 구매형**(발주처가 인원·금액으로 계약·일괄 지급, 세금계산서, 임직원은 선택·수령만). 복지포인트·개인 결제형은 소비자 대상 통신판매라 7단계 자체 결제와 함께 검토.
- 구성: 전용 주소(`/corp/{발주처}` 또는 하위 도메인, 검색 노출 차단·발주처 로고) / 명단 기반 개인별 1회용 링크·코드 입장(회원가입 없음, 필요 시 회사 메일 코드 인증) / 낙찰 제안서 상품만 진열(금액대별 선택형) / 실물은 협력업체·위탁 공급사로 발주(발주 자동화 재사용), 모바일 쿠폰은 쿠폰 API로 즉시 발송 / 선택 마감·마감 전 알림·미선택자 기본 상품 처리 / 발주처 담당자 화면(선택률·발송·배송·정산·명단 수정 요청) / CS는 B2B 창구 폐쇄몰 분야 / 알림은 알림톡+문자 대체.
- 모바일 쿠폰 API: 확인된 곳 **기프티쇼 비즈(KT alpha)** — 약 120개 브랜드·6,000개 상품, 직접 MMS 발송·쿠폰 이미지 개별 전달·PIN으로 바코드 생성, 취소·재발송(상품 목록·상태 조회 API·가입 조건·선불 충전 방식은 오픈 API 문서·영업 문의로 확인). 쿠프마케팅·윈큐브마케팅 등은 기업 연동 조건을 문의해 비교. 카카오톡 선물하기 기업용은 연동 API 여부 미확인.
- 운영 규칙: 쿠폰 선불 충전은 발주처 대금 수령 후 / 발송 기록(대상·시각·쿠폰·사용 여부) / 미사용·만료 처리는 쿠폰사 조건과 발주처 계약을 맞춤 / 제안서 가격 비교에 쿠팡 시장가를 쓰되 사업용 구매에 쿠팡 파트너스 링크는 쓰지 않음.
- 개인정보: 임직원 명단(이름·휴대폰·배송지)은 발주처 위탁 → 운영사 수탁자, 필요한 항목만, 발주처별 분리 저장, 계약 종료 후 기간 경과 시 파기, 쿠폰사·공급사 전달은 재위탁이므로 발주처 동의를 계약에 포함.
- 입찰 전 확인: 운영사의 사업자등록·공공 조달 등록(공고 요건). 제안서 템플릿에 폐쇄몰 항목(개설 소요일·선택 기한·CS 응답 기준·개인정보 처리) 포함.
- 시작 전 결정: 쿠폰사 선정(연동 조건·선불 충전·미사용 처리 비교), 발주처 계약 표준안(기본 상품·하자·위탁·재위탁 동의).

## 7단계 역직구 시범 통과 조건
설계 문서 부록 C의 라스트마일 경계(누락·충돌·정정)를 시범의 명시적 통과 조건으로 씁니다.
- 운송사의 '배달 완료' 보고만으로 고객 수령을 확정하지 않음. 화면·CS 답변·셀러 SCM에서 **운송사 보고 / 수취 확인 / 최종 인도 증거**가 따로 표시되는지 검증.
- 구간별 증거(국내 출고 → 국제 운송 → 통관 → 현지 배송 → 인도) 중 빠진 구간이 있으면 "확인되지 않음"으로 표시되고 완료로 처리되지 않음.
- 기록 충돌(운송사는 배달 완료, 고객은 미수령)이 생기면 자동 종결되지 않고 정해진 처리 주체·기한으로 넘어감.
- 기록 정정(운송사 이벤트 수정·취소)이 이력으로 남고 이전 상태를 덮어쓰지 않음.
- 분실·오배송·통관 보류·반송 시나리오를 시범 전 테스트 데이터로 통과.
