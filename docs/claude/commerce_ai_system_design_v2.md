# commerce\_ai 전체 시스템 설계 v2

Nov 9, 2026 · @Ason

commerce\_ai는 하나의 대화형 오케스트레이터 아래 B2C 추천·트렌드 콘텐츠, 입점 셀러 AI 쇼핑몰, 해외 직구·역직구, B2B 입찰 사업, 공통 CS를 두는 **제품 구상**입니다. 네이버 쇼핑커넥트는 외부 웹사이트 사용 불가 회신에 따라 사이트에서 제외하고, 사이트 제휴 링크는 쿠팡 파트너스 약관·승인된 API 범위·광고 표시를 확인한 뒤 운영합니다. 로드맵과 데이터 모델은 구현 완료 목록이 아니라 설계안입니다.

**읽는 법** — **확인**은 열람한 설계 결정·공식 자료가 뒷받침하는 내용, **설계안**은 채택 전 제품 후보, **미해결**은 권한·계약·정책 확인이 필요한 내용입니다. 법규·운송 서비스·API 접근 조건은 출하 직전에 다시 확인합니다. 개발용 근거(추천 엔진 경계, 해외 거래 데이터 계약, 라스트마일 증거)는 문서 끝 부록에 둡니다.

## 핵심 변경 8가지

기존 "공통 코어 1개, 앱 2개"(consumer · b2b)를 바탕으로 seller · admin 앱과 회원·CS·콘텐츠 모듈을 더하는 **논리적 설계안**입니다. 한 저장소·한 DB, 스키마 분리, 통합 대화 라우터는 배포·권한·데이터 분리 검토가 남은 선택지입니다.

1. **트렌드 글의 무대를 사이트로 옮김** — trendguide 게시를 제안하되(트렌드 리포트 링크는 쿠팡 링크로 대체, 대화창에서 글 Q&A·원문 보기 제공) 초안 검토, 제휴 표시·링크 정책과 권리 검증 후 공개합니다. 네이버 쇼핑커넥트는 확인된 채널 범위(네이버 안)에서만 씁니다.
2. **회원 계정과 개인화** — 개인정보를 받지 않는 SSO 로그인(구글·Microsoft·카카오·네이버)과 계정 복구 수단을 두고, 로그인한 고객에게 마이 대시보드를 제공하되, 고객이 관심을 보인 트렌드만 제한적으로 보여 줍니다.
3. **입점 셀러 AI 쇼핑몰** — 업체가 사진·기본 정보만 올리면 AI가 상세페이지와 미니샵 초안을 만들고, 셀러 확인과 운영자 승인 후 공개합니다. 셀러는 SCM 페이지에서 승인 상태·재고·판매·결제·배송을 관리합니다.
4. **해외배송: 직구·역직구** — 해외 상품 발견·직구 연결, 구매대행, 국내 상품 역직구를 별도 사업 모델로 검토합니다. 국제 운송부터 도착국 마지막 배송·수령까지 증거를 연결하는 설계를 포함합니다.
5. **B2B를 4단계 사업 파이프라인으로** — 공고 분석 → 협력업체 분석 → 소싱 협력 → 제안서. 한 공고가 단계를 따라 흐르는 "입찰 건(Deal)" 단위로 관리합니다.
6. **B2B 작업 유형 레지스트리** — 제안서뿐 아니라 적격성 판정, 질의서, 견적 비교, 발표자료 등을 작업 유형으로 등록해 같은 대화창에서 처리합니다.
7. **공통 CS 모듈** — B2C·B2B·셀러 문의를 하나의 티켓 체계로 받고, AI 1차 응답 후 확신이 낮으면 운영자에게 넘깁니다.
8. **UCP는 단계적으로** — 검색 노출, UCP 카탈로그 공개, UCP 결제를 별개로 보고, 프로필·HTTPS·접근 권한·판매 주체·참여 요건을 각각 확인해 승인합니다.

## 전체 구조도

고객 웹·셀러 센터·운영자 화면·외부 AI 에이전트가 하나의 대화 라우터를 거쳐 7개 도메인 서비스로 가는 **목표 구조**입니다. 외부 에이전트 접근과 B2B 운영자 권한은 별도 인증·인가 경계가 필요하고, core·콘텐츠·b2b 스키마 분리는 채택 전 설계안입니다.

## B2C 트렌드 글 자동화

트렌드 감지부터 사이트 게시까지의 **후보 흐름**입니다. 초안·출처·제휴 정책을 운영자가 승인한 뒤 공개하고, 자동 게시 전환은 정확도·권리·정책·운영 이력을 따로 검토해 결정합니다.

**파이프라인 (매일 1회, 서버 스케줄러)**

1. **감지** — 네이버 데이터랩, YouTube Data API, 블로그 언급량에서 급상승 요리·식재료 후보를 뽑습니다 (두쫀쿠 같은 신규 요리 포함).
2. **선별** — 최근 게시 주제와 겹치거나 주류 관련이면 제외하고, 상위 후보만 남깁니다.
3. **레시피 매칭** — 식품안전나라·농식품정보누리(EPIS) 공공 레시피를 원본으로 붙이고, 빠진 단계는 '일반 조리 제안(원문 아님)'으로 보완합니다.
4. **상품 매칭** — 재료별로 쿠팡 파트너스 API에서 상품을 찾고, KAMIS 참고 시세는 따로 보존합니다. 공공 시세가 특정 상품의 가격 적정성을 증명하지 않으며, 제휴 여부가 일반 추천 순위를 정하지 않도록 검증합니다.
5. **글 생성** — 고정 템플릿(트렌드 이유 → 레시피 요약 → 재료·상품 → 가격 참고)으로 초안을 만듭니다.
6. **정책 검사** — 아래 규칙을 후보 검사로 두고, 위반·미확인은 게시하지 않고 검토 대기로 보냅니다. 자동 검사가 권리·약관 준수를 최종 인증하지는 않습니다.
7. **게시** — `/trends/{날짜}-{주제}` 페이지로 공개하고, 사이트맵·구조화 데이터를 갱신해 검색 노출을 돕습니다.
8. **블로그용 사본** — 같은 글을 네이버 블로그 서식으로 변환해 관리자 화면에 두고, 직접 복사해 올립니다 (캡차 때문에 자동 게시하지 않음).
9. **성과 기록** — 조회·클릭을 자체 로그에 남기고, 쿠팡 정산 데이터와 합쳐 관리자 분석 화면에 보여 줍니다.

**정책 검사 항목 (게시 차단 조건)**

| 항목 | 규칙 |
| --- | --- |
| 광고 표시 | 제목에 \[광고\], 본문 맨 위에 쿠팡 대가성 문구와 "수수료는 사이트 무료 운영에 도움" 문구 |
| 링크 방식 | 고객이 직접 누르는 링크만 허용. 자동 이동·숨김 링크·팝업 금지 (쿠팡은 이른바 납치광고에 형사 고소까지 진행) |
| 금지 주제 | 주류 관련 글에는 상품 링크 없음 |
| 레시피 출처 | 원문 출처 한 줄과 '참고했으며 원문 그대로가 아님' 표기 |
| 숫자 검증 | 가격·평점 등 숫자는 검증 로그에 있는 값만. 스크래핑 평점은 사용 안 함 |
| 중복 | 최근 30일 같은 주제 글이 있으면 갱신으로 처리 |

쿠팡 제휴 운영은 2026-11 회신에서 확인한 웹사이트 사용 조건, 광고 표시, 최종 승인된 API 접근 범위를 기준으로 검사합니다. 제재 횟수·정산 처리에 관한 보도 내용은 계약상 확정 규칙으로 코드화하지 않고, 실제 계정 약관과 최신 정책을 운영자가 확인합니다.

### 트렌드 글 Q&A — 분석 답변과 원문 보기

고객이 대화창에서 트렌드에 대해 물으면, commerce\_ai LLM이 게시된 트렌드 글을 찾아 분석한 답을 주고 근거가 된 글 원문을 바로 띄워 줍니다.

1. **검색** — 운영자 승인을 거쳐 게시된 트렌드 글만 색인합니다 (제목·요약·재료·레시피·태그, 문장 단위 임베딩). 검토 대기·반려 글은 답변 근거로 쓰지 않습니다.
2. **분석 답변** — 찾은 글 내용만 근거로 답하고, 문장마다 근거 글(제목·게시일)을 표시합니다. 예: "요즘 두쫀쿠가 왜 유행해?", "이 레시피 재료비는 얼마쯤 들어?", "지난달 디저트 트렌드랑 뭐가 달라?" 가격·시세는 글에 적힌 기준 시각을 함께 말합니다.
3. **원문 보기** — 답변 아래 근거 글 카드를 두고, 누르면 같은 화면 옆 패널(모바일은 전체 화면)에 글 원문을 띄웁니다. 원문에는 게시된 그대로 \[광고\] 표시·대가성 문구·쿠팡 링크·레시피 출처가 함께 나옵니다.
4. **근거가 없을 때** — 관련 글이 없으면 지어내지 않고 "관련 트렌드 글이 아직 없습니다"라고 답한 뒤 일반 상품 추천 대화로 넘깁니다.
5. **외부 원천** — 트렌드 감지에 쓴 블로그·YouTube 등 외부 글은 본문을 옮겨 싣지 않고 제목·링크·짧은 요약만 보여 줍니다.

이 기능은 작업 유형 레지스트리에 '트렌드 글 Q&A' 유형으로 등록하고, 질문 → 열어 본 원문 → 상품 클릭을 함께 기록해 어떤 글이 답변에 쓰였는지 관리자 화면에서 봅니다.

### trendguide.kr 링크 원칙

trendguide.kr에서는 트렌드 리포트(네이버 블로그 등 외부 리포트)로 보내는 링크를 두지 않고, 그 자리를 쿠팡 파트너스 상품 링크로 대체합니다. 링크마다 광고 표시와 대가성 문구를 유지하고, 고객이 직접 누르는 링크만 씁니다. 트렌드 내용은 사이트 안의 글과 Q&A로 보여 줍니다.

## 회원 개인화와 대시보드

로그인은 선택이고, 비회원도 추천·트렌드 글을 모두 쓸 수 있습니다. 로그인하면 "내가 저장한 것과 알려 주길 원한 것"을 모아 보여 주는 대시보드가 생깁니다.

| 대시보드 영역 | 내용 | 쓰는 데이터 |
| --- | --- | --- |
| 관심 트렌드 | 고객이 관심을 보인 트렌드만 최근 5개 이내로 요약 카드 + 원문 링크 (전체 트렌드 목록은 보여 주지 않음) | 관심 신호 (직접 고른 분야, 저장한 글, 대화에서 물어본 주제), 게시된 트렌드 글 |
| 저장 레시피 | 북마크한 레시피와 장보기 목록 | 저장 기록 |
| 가격 알림 | 지정한 식재료의 KAMIS 시세가 기준 이하로 내려가면 표시 | 알림 설정, KAMIS |
| 최근 본 상품 | 명시적 상품 상세 조회가 기록된 경우에만 표시 | 조회 이벤트 (동의·보존기간 검토). 클릭만으로 조회를 추정하지 않음 |
| 주문·문의 | 직판·입점 상품 주문 상태, CS 문의 진행 상황 (직판 시작 후) | 주문, CS 티켓 |
| 내 정보 | 수신 동의, 데이터 삭제 요청 | 계정 |

**설계 원칙**

- **관심 트렌드만 제한적으로** — 대시보드에는 고객이 관심을 보인 트렌드만 보여 줍니다. 관심 신호는 직접 고른 분야, 저장한 글, 대화에서 물어본 주제이고, 최근 5개 이내 요약 카드와 원문 링크만 냅니다. 전체 트렌드 목록, 트렌드 감지 수치·순위, 내부 분석 데이터는 대시보드로 제공하지 않습니다.
- **개인화는 정렬에만** — 관심사와 이력은 글·상품의 노출 순서를 바꾸는 데만 쓰고, 제휴 여부와 섞지 않습니다.
- **최소 수집** — SSO 고유 식별자와 관심 신호만 저장하고 이름·이메일·전화번호는 받지 않습니다. 주소·연락처는 주문이 생길 때 그 주문에만 받습니다.
- **동의 분리** — 서비스 이용 동의와 마케팅 수신 동의를 나누고, 대시보드에서 언제든 관심 신호를 지우거나 철회·삭제할 수 있게 합니다.
- **제휴 부정 이용 방지 (설계안)** — 약관상 자기 구매·유도 금지를 운영 절차로 점검합니다. 가구 관계를 계정 속성으로 추정·수집하는 방안은 개인정보 필요성·동의·정확도 검토 전에는 채택하지 않습니다.

연락처를 받지 않으므로 알림은 사이트 안 알림만 씁니다. 이메일 알림은 고객이 원할 때만 주소를 따로 입력하고 동의하는 선택 기능으로 둡니다. 메신저 알림은 '카카오톡·네이버 톡톡 연계 검토' 절에서 다룹니다.

### SSO 로그인과 계정 복구

자체 회원가입과 비밀번호는 두지 않고 구글·Microsoft·카카오·네이버 SSO로만 로그인합니다. 이름·이메일·전화번호·생년월일은 받지 않고, 공급자가 주는 고유 식별자만 저장합니다.

| 공급자 | 요청 범위 | commerce\_ai가 저장하는 값 |
| --- | --- | --- |
| 구글 | OpenID Connect `openid`만 (이메일·프로필 범위 요청 안 함) | 공급자 고유 ID |
| Microsoft | `openid`만 | 공급자 고유 ID |
| 카카오 | 카카오 로그인 동의 항목 최소 설정 (프로필·이메일 미요청) | 회원번호 |
| 네이버 | 네이버 로그인 제공 정보 최소 설정 | 고유 ID |

공급자별 필수 동의 항목과 최소 요청 범위는 앱 등록 시 확인합니다. 받은 값이 있더라도 위 고유 ID 외에는 저장하지 않습니다.

**저장하는 것** — 내부 계정 번호(무작위), 연결된 공급자와 고유 ID(키를 건 해시로 저장), 고객이 직접 정하는 별칭(선택), 관심 신호. 고유 ID와 이용 기록도 개인정보에 해당할 수 있으므로, 수집 항목은 적어도 개인정보 처리방침·동의·보존기간은 갖춥니다 (법률 검토 필요).

**로그인 흐름** — 공급자 선택 → 공급자 인증(state·nonce·PKCE 검증) → 고유 ID로 계정을 찾거나 새로 만듦 → 보안 세션 쿠키(httponly·secure·samesite) 발급.

**계정·로그인 정보 분실 처리**

commerce\_ai는 비밀번호도 연락처도 갖고 있지 않으므로, 복구는 "다른 로그인 수단"과 "복구 코드"로만 합니다.

| 상황 | 처리 |
| --- | --- |
| 어느 SSO로 가입했는지 잊음 | 로그인 화면의 4개 버튼 중 연결된 어느 공급자로든 로그인됩니다. 이 기기에서 마지막에 쓴 공급자를 브라우저에만 기억해 강조 표시합니다 |
| 공급자 계정 비밀번호 분실 | 해당 공급자의 계정 찾기로 복구하도록 안내 링크를 줍니다. commerce\_ai는 비밀번호를 보관하지 않습니다 |
| 공급자 계정을 잃거나 탈퇴함 | 미리 연결해 둔 다른 공급자로 로그인하거나 복구 코드를 입력해 새 공급자를 연결합니다 |
| 복구 코드 분실 | 로그인된 상태에서 새로 발급합니다 (이전 코드는 즉시 무효) |
| 연결된 공급자를 모두 잃고 복구 코드도 없음 | 본인을 확인할 수단이 없어 복구할 수 없습니다. 새 계정으로 시작하고, 관심 기록은 옮기지 않습니다. 직판 시작 뒤의 주문은 주문번호와 결제 정보로 CS가 확인합니다 |
| 다른 공급자로 실수로 새 계정을 만듦 | 두 계정에 모두 로그인한 상태에서 '계정 합치기'로 관심 기록과 저장 레시피를 합칩니다 |

**분실 예방**

- **두 번째 로그인 연결 권유** — 가입 직후와 대시보드 '내 정보'에서 다른 공급자를 추가로 연결하게 안내합니다. 연결은 최소 1개 유지해야 해제할 수 있습니다.
- **복구 코드** — 가입 시 복구 코드를 한 번만 보여 주고 복사·저장하게 합니다. 서버에는 해시만 저장하고, 사용하면 새 코드를 발급합니다.
- **변경 알림** — 공급자 연결·해제, 복구 코드 사용이 일어나면 사이트 안 알림으로 알립니다. 공급자 쪽 2단계 인증 사용도 권장합니다.
- **탈퇴** — 즉시 계정과 관심 기록을 삭제하고, 법정 보존 대상(주문·결제 기록)만 분리 보관 후 기한이 지나면 파기합니다.

**셀러·운영자 계정**

- **입점 셀러** — 같은 SSO로 로그인하되, 입점 계약에 필요한 사업자 정보(상호·사업자등록번호·담당자 연락처)는 셀러 계정에서만 받습니다. 한 업체에 담당자 SSO 계정을 여러 개 연결하고 권한을 나눕니다. 담당자가 로그인 수단을 잃으면 업체 관리자 담당자가 다시 연결하고, 관리자가 잃으면 운영자가 사업자 확인 후 관리자를 다시 지정합니다.
- **운영자·B2B** — 허용 목록에 등록된 SSO 계정만 로그인하고, 공급자 쪽 2단계 인증을 필수로 합니다.

## 입점 셀러 AI 쇼핑몰

입점 업체는 사진과 기본 정보만 올리고, 상세페이지·미니샵·카탈로그 데이터는 AI가 초안을 만듭니다. 업체가 수정·확인한 뒤 운영자가 승인해야 공개하는 설계안이며, 판매자 표시·결제·환불 책임은 계약과 판매 방식별로 확정합니다.

**셀러 흐름**

1. **입점 신청** — 상호·대표자·사업자등록번호·통신판매업 신고번호·연락처 등록. 판매 당사자 정보가 없으면 상품을 공개하지 않습니다.
2. **상품 등록** — 사진, 상품명, 가격, 원산지·용량, 배송 조건을 입력하거나 엑셀로 올립니다.
3. **AI 상세페이지 생성** — 기본 템플릿에서 상세페이지 초안을 만들고, 품목별 표시 의무 필드가 비면 공개를 보류하고 셀러에게 증빙 입력을 요청합니다. AI가 인증·원산지·유통기한을 만들어 넣지 않습니다.
4. **AI 미니샵 생성** — 업체 소개, 대표 상품, 분류를 묶어 `/shop/{업체}` 페이지를 만듭니다.
5. **셀러 확인** — 업체가 문구를 수정하고 "내용이 사실과 같음"을 확인합니다.
6. **운영자 승인** — 과장 표현·법정 표시 누락 검사를 통과하면 공개합니다.
7. **공개 이후** — 검증된 판매자·상품과 공개 승인을 통과한 채널에만 노출합니다. UCP 카탈로그 노출은 별도 권한·역할·호환성 검증 전에는 보장하지 않습니다.

**셀러 센터 기능 (단계별)**

| 기능 | 1단계 (베타) | 2단계 (정식) |
| --- | --- | --- |
| 상품·상세페이지 | AI 초안 생성, 수정, 승인 요청 | 템플릿 선택, 다국어(영문) 상세페이지 |
| 미니샵 | 기본 레이아웃 1종 | 배너·기획전 |
| 주문 | 판매자 사이트로 이동 (결제는 업체 쪽) | commerce\_ai 결제 (PG 계약 후) |
| 성과 | 조회·클릭 수 | 매출·전환율, 트렌드 연계 추천 |
| 문의 | 고객 문의 티켓 수신·답변 | 답변 초안 AI 제안 |

1단계에서 결제를 업체 사이트로 보내는 것은 청약 접수·대금 수령의 경계를 분명히 하기 위한 설계안입니다 (판매 유형 설계서, 2026-11-06). 실제 판매자·중개자 의무는 서비스 동작·약관·계약에 따라 검토합니다. 직접판매·구매대행·입점·제휴는 판매 주체, 주문·결제 책임, 반품·CS 경계를 별도 속성으로 유지하고, 화면 배지는 그 사실을 표시하는 수단일 뿐 순위에서 우대하지 않습니다.

### 입점 셀러 SCM 페이지

입점 셀러는 `/seller/scm`에서 자기 상품의 승인 상태, 재고, 주문·판매, 결제·정산, 배송을 한 화면에서 관리합니다. 셀러는 자기 업체 데이터만 볼 수 있고, 운영자는 전체를 봅니다.

| 메뉴 | 셀러가 하는 일 | 데이터 원천 | 시작 단계 |
| --- | --- | --- | --- |
| 운영자 승인 현황 | 입점·상품별 심사 상태(대기 / 보완 요청 / 승인 / 반려)와 사유 확인, 보완 제출 | 승인 워크플로 | 1단계 (베타) |
| 상품·재고 관리 | 상품 수정, 옵션별 재고 입력·엑셀 일괄 수정, 품절 예정 알림. 재고 0이면 자동으로 노출 중지 | 셀러 입력 | 1단계 (베타) |
| 판매 현황 | 기간·상품별 조회·클릭·주문 수·매출, 취소·반품 | 1단계: 조회·클릭 + 셀러가 올린 판매 보고 / 2단계: commerce\_ai 주문 | 1단계부터 |
| 결제·정산 현황 | 결제 완료·취소, 정산 예정액, 수수료, 지급일 | PG 정산 데이터 | 2단계 (commerce\_ai 결제 시작 후). 1단계에는 "결제는 업체 사이트에서 처리"로 표시 |
| 택배 조회 | 송장 번호 등록, 배송 단계 조회, 지연·미수령 알림 | 택배사 배송 조회 API (연동 업체 선정 필요) | 송장 등록 1단계, 자동 조회 2단계 |
| 문의·CS | 고객 문의 티켓 답변, 운영자 이관 | CS 모듈 | 1단계 |
| 성과 분석 | 트렌드 글·Q&A에서 들어온 유입, 전환율 | 클릭·주문 로그 | 2단계 |
| 설정 | 배송·반품 정책, 반품지 주소, 담당자 계정·권한 | 셀러 입력 | 1단계 |

- **권한 분리** — 셀러 계정은 자기 업체 데이터만 조회·수정하고, 담당자별로 조회 전용 / 상품 관리 / 정산 열람 권한을 나눕니다.
- **고객 개인정보 최소화** — 셀러에게는 배송에 필요한 수령인 정보만 보여 주고, 배송 완료 후 정해진 기간이 지나면 가립니다.
- **재고와 노출 연동** — 재고·판매 중지 상태가 바뀌면 사이트·트렌드 글·Q&A 답변·UCP 카탈로그 노출에 함께 반영합니다.
- **해외 판매** — 역직구에 참여하는 셀러는 같은 SCM에서 해외 주문·국제 송장·통관 상태를 따로 봅니다 (출하 게이트 통과 후).

## 해외배송: 직구·역직구

해외 거래는 **해외 판매처로 보내는 직구 안내**, 별도 계약과 책임이 따르는 **구매대행**, **국내 출고 역직구**로 나눕니다. 상품 발견, 추천 판단, 판매자, 주문 주체, 통관 당사자, 운송 계약자, 현지 마지막 배송 책임이 각각 다르기 때문입니다. 현재는 조사·설계 단계이며 실제 거래·운송 연동은 미확인입니다.

| 구분 | 직구 (해외 → 한국) | 역직구 (한국 → 해외) |
| --- | --- | --- |
| 고객 | 국내 고객 | 해외 고객 (해외 IP·영문 화면) |
| 상품 원천 | 해외 Shopify 상점 (Global Catalog) | 입점 셀러·B2B 협력업체·직접 소싱 |
| 인기 신호 | 출처와 접근 권한이 확인된 검색·콘텐츠 신호 후보 | 출처와 접근 권한이 확인된 국가별 수요 신호 후보. 상품 동일성·노출 분모 확인 필요 |
| 판매 유형 | 직구 연결(판매처 이동) 또는 구매대행 | 직접판매 또는 중개(입점) |
| 배송 | 상점 직배송 또는 배송대행지 경유 | 우체국 EMS·K-Packet, 포워딩 |
| 통관 핵심 | 고객의 수입자 지위·개인통관고유부호·품목별 목록통관/수입신고 판단. 150달러(미국발 200달러) 목록통관 기준은 품목·절차별 예외 확인 필요 | 한국 수출 절차, 도착국 수입자·품목 규정, 관세·세금·수수료의 납부 주체 확인 |

### 직구: 해외 Shopify 인기 상품 찾기

기존 UCP 카탈로그 어댑터(미연결·기본 꺼짐)를 출발점으로 Shopify Global Catalog의 호환성·프로필·접근 권한을 따로 검증합니다. Global Catalog는 여러 Shopify 상점을 한 번에 검색하고 **배송 가능 국가(ships\_to)**·출고 국가·가격·평점 필터를 지원하며, 쓰려면 commerce\_ai의 에이전트 프로필이 필요합니다 ([Shopify 문서](https://shopify.dev/docs/agents/catalog/global-catalog)).

- **한국 배송 가능 상품만 먼저** — `ships_to: KR`은 발견 단계의 필터입니다. 옵션·재고·배송지별 최종 배송 가능 여부와 비용은 판매처 결제 화면에서 다시 확인합니다.
- **인기 순위는 직접 계산** — 공식 문서에 판매량 정렬이 없으므로 평점·상점 수 등 API가 실제로 주는 값과 출처 있는 신호만 후보로 씁니다. 자체 클릭은 노출 수(분모)가 검증되지 않으면 인기 근거로 쓰지 않습니다. 상품 동일성·중복 상점·시점·불확실성을 보존하고, 추천 점수에 넣을지는 따로 결정합니다.
- **구매 방식 2가지**
  1. **직구 연결** — 한국 배송 상점이면 상품 결제 링크로 보내고 고객이 직접 결제합니다. 화면에 예상 관부가세, 면세 한도, 개인통관고유부호 필요를 안내합니다.
  2. **구매대행** — 한국 배송이 안 되거나 고객이 원하면 판매 유형 설계서의 구매대행으로 처리합니다 (가격 구성표, 주문별 고객 명의 통관).
- **식품 제한 유지** — 해외 식품 구매대행은 영업등록 확인 전 비활성. 건강기능식품의 수량·품목 제한은 관세청과 관계기관의 최신 안내를 주문별로 확인합니다.
- **수익 구조** — 직구 연결은 수수료가 없을 수 있어 유입·신뢰용이고, 수익은 구매대행 수수료에서 납니다.

### 역직구: 해외에서 인기 있는 국내 상품 팔기

1. **해외 인기 K-상품 감지** — Global Catalog에서 출고국이 한국인 상품과 해외 상점이 파는 한국 상품의 평점·취급 수, 국가별 YouTube 인기 영상의 한국 음식·제품, 해외 방문자 검색어를 모아 후보 목록을 만듭니다.
2. **국내 공급처 매칭** — 입점 셀러와 B2B 협력업체 후보를 상품·법적 주체·공급 능력 근거로 대조합니다. 등록부에 있다는 것만으로 해외 판매 권한이나 같은 상품임을 확정하지 않습니다.
3. **해외용 상품 페이지** — AI 영문 초안은 원본·셀러 확인 뒤 공개합니다. 상품가, 국제·현지 운임, 관세·세금, 수수료는 납부자와 견적/확정 상태를 나눠 표시합니다.
4. **국가별 규정 검사** — 상품·도착국·운송 서비스별 적용 규칙과 근거를 모읍니다. 레지스트리만으로 적법성을 자동 확정하지 않고, 미확인 조합은 공개를 보류합니다.
5. **결제** — 해외 카드를 받는 결제대행 계약 (국내 PG의 해외 결제 또는 글로벌 PG, 확인 필요).
6. **배송** — 우체국 EMS·K-Packet과 포워딩. 미국행 우체국 서비스는 발송인 관세·수수료 선납 방식을 안내하지만, 접수 가능 서비스·품목·금액·정산·현지 배송 조건은 발송 시점 공식 안내와 계약으로 확인합니다. 수취인 추가 청구 여부는 적용된 상품·서비스·납부 계약의 결과로만 표시합니다.

**식품 역직구의 핵심 제약 (미국 기준).** FDA 시설 등록과 Prior Notice(사전신고)의 적용·면제 여부를 품목·제조 시설·수입자·배송 방식별로 확인하고, 라벨·알레르겐과 다른 기관 규정도 따로 점검합니다. 등록번호나 신고 접수가 통관·판매 허가를 보장하지는 않습니다. **비식품을 먼저** 하고, 상온 포장 식품은 품목별 검토를 마친 뒤 후보로 두며, 신선·냉장은 제외합니다.

| 미국행 규정 검증 | 공식 자료와 설계 처리 |
| --- | --- |
| 관세·수수료 | 미국 CBP는 2025-08-29부터 저가물품 면세를 중단했습니다 ([CBP 안내](https://www.cbp.gov/sites/default/files/2025-08/factsheet_suspension_of_duty-free_de_minimis_treatment.pdf)). "800달러 이하 면세" 문구는 쓰지 않고, 품목·원산지·통관 방식·날짜별로 산정합니다 |
| 우체국 관세 선납 | 우정사업본부 미국행 선납 안내([공지](https://ems.epost.go.kr/epost.go.kr/front.EmsNewsDetail.postal?db=notice&seq=1343))는 해당 접수 상품 조건으로만 적용. 모든 서비스·품목에 "도착 후 추가 청구 없음"으로 일반화하지 않습니다 |
| 식품 | FDA 등록·Prior Notice 적용/면제와 신고 시점을 품목별로 확인([FDA Prior Notice](https://www.fda.gov/industry/prior-notice-imported-foods/filing-prior-notice-imported-foods)). 증빙 없이 식품 후보를 판매 가능으로 게시하지 않습니다 |

**출하 게이트** — 첫 시범은 1개 도착국·1개 운송 서비스·비식품으로 하고, 주문·포장 단위 추적과 미수령·반송 케이스를 수동 검증한 뒤 확대 여부를 정합니다. 그 전에 도착국 우편번호·품목·현지 배송망·반송 경로·수입자·납부 주체·배송 증빙(POD) 제공 범위·추적 API 사용권을 계약이나 공식 안내로 확인하고, 현지 배송비·통관 수수료·외곽 추가비·보관·반송 비용을 따로 견적합니다. 해외 거래 데이터 계약과 라스트마일 증거 설계는 부록에 있습니다.

### Shopify 상점으로 에이전트 노출 넓히기

한국 출고 Shopify 상점은 **별도 채널 후보**입니다. Global Catalog 노출은 상점 자격·상품 공개·국가별 가용성을 검증해야 하고, 자체 UCP 프로필 공개와 자동으로 연동되지 않습니다. Google UCP 결제의 참여 조건은 최신 공식 요건으로 확인하고, 역직구 자체 결제도 PG·판매자·반품·현지 배송·규제 게이트를 통과한 뒤에 설계합니다.

## B2B 사업화 파이프라인

공고 하나를 "입찰 건(Deal)"으로 만들고, 4단계를 거치며 각 단계 끝에 진행·보류·포기를 결정합니다. 지금의 콘솔 도구(analyze · sourcing · cost · rfq · proposal)는 그대로 쓰고, 이것들을 단계 순서로 묶는 것이 이번 변경입니다.

| 단계 | 입력 | AI가 하는 일 | 산출물 | 넘어가는 조건 (게이트) |
| --- | --- | --- | --- | --- |
| 1. 공고 분석 | 나라장터 API 공고, 원문 첨부(HWPX·PDF·DOCX) | 자격요건·예산·수량·마감·평가 기준·필수 서류를 원문 발췌와 함께 구조화. 회사 프로필과 대조해 적격성 판정 | 공고 분석표, 적격성(ELIGIBLE / HOLD / EXCLUDED), 질의할 항목 | 자격 미달 없음 + 마감까지 준비 기간 충분 |
| 2. 협력업체 분석 | 공고 요구 품목, 협력업체 등록부 | 품목별 후보 업체를 찾고 공급 능력·인증·가격대·납기·과거 거래를 비교 | 품목별 후보 비교표, 부족 품목 목록 | 모든 필수 품목에 후보 2곳 이상 |
| 3. 상품 소싱 협력 | 후보 업체, 수량·납기 | 업체별 견적 요청서 초안, 회신(메일·엑셀·PDF) 파싱, 견적 비교, 1인 비용 구조 계산 | 확정 견적, 원가·마진표, 공급 확약 여부 | 확정 견적으로 마진 확보 + 공급 확약 |
| 4. 제안서 작성 | 1\~3단계 결과, 회사 프로필, 템플릿 | 요구사항 대응표, 상품 구성안, 가격 제안, 운영·CS 계획 작성. 모르는 값은 \[확인 필요\] | 제안서 (pptx·hwpx·pdf·html), 제출 체크리스트 | 확인 필요 0건 + 운영자 최종 검토 |

**설계 포인트**

- **입찰 건 단위 저장** — 공고·분석·후보·견적·제안서 버전·결정 기록을 한 Deal에 묶어, 언제든 "이 건 어디까지 왔지?"를 볼 수 있게 합니다.
- **협력업체 등록부를 사업 자산으로** — 업체 정보, 취급 품목, 견적 이력, 응답 속도, 거래 결과를 쌓습니다. 입점 셀러와 B2B 공급업체는 법적 주체·운영 장소·계약 역할을 따로 검증하고, 같은 사업자임이 입증될 때만 출처 있는 관계로 연결합니다. 공통 업체 마스터는 미결정입니다.
- **수주 이후 단계 예약** — 5단계(계약·납품 관리)와 6단계(정산·실적 기록)는 자리만 두고, 첫 수주 뒤 만듭니다. 실적은 다음 제안서의 회사 소개에 반영합니다.
- **외부 발송 없음 유지** — 견적 요청·제안서는 모두 초안 파일이고, 보내는 것은 운영자가 직접 합니다.

## B2B 작업 유형 레지스트리

B2B 대화창은 "제안서 써줘" 하나가 아니라 여러 종류의 요청을 받아야 하므로, 요청마다 프롬프트를 새로 짜지 않고 **작업 유형**을 등록해 두고 고릅니다. 새 업무가 생기면 코드 수정 없이 유형 하나(설정 파일 1개)를 추가합니다.

**작업 유형 하나의 구성**

- `id`·설명·예시 문장 — 대화 라우터가 요청을 이 유형으로 분류하는 데 씀
- 필요한 입력 — 예: Deal, 공고 원문, 후보 업체. 빠지면 먼저 되묻기
- 사용하는 도구 — analyze, sourcing, cost, rfq, proposal, 문서 생성 등
- 프롬프트 템플릿 — 역할, 근거 사용 규칙(원문 발췌 필수, 모르면 \[확인 필요\]), 출력 형식
- 출력 형식과 검사 — 표·문서·파일 종류, 숫자 지어내기 검사
- 위험 등급 — 초안만 / 운영자 확인 필수

**1차로 등록할 작업 유형**

| 단계 | 작업 유형 | 요청 예 | 출력 |
| --- | --- | --- | --- |
| 1 | 공고 요약 | "이 공고 3줄로 요약해줘" | 요약 + 핵심 일정 |
| 1 | 적격성 판정 | "우리가 참여 가능해?" | 요건별 충족·미확인·위반 표 |
| 1 | 질의서 작성 | "발주처에 물어볼 것 정리해줘" | 질의 공문 초안 |
| 1 | 평가 기준 대응 전략 | "배점 높은 항목 위주로 전략 짜줘" | 항목별 대응 포인트 |
| 2 | 협력업체 비교 | "과일 선물세트 업체 비교해줘" | 후보 비교표 |
| 2 | 신규 업체 발굴 | "한우 공급처 더 찾아줘" | 후보 목록 + 확인 항목 |
| 3 | 견적 요청서 | "3개 업체에 보낼 견적 요청서" | 업체별 메일 초안 |
| 3 | 견적 비교·원가 계산 | "회신 온 견적 비교해줘" | 비교표 + 1인 비용 구조 |
| 3 | 협상 메일 | "단가 5% 조정 요청 메일" | 메일 초안 |
| 4 | 제안서 작성 | "제안서 만들어줘" | 제안서 파일 |
| 4 | 발표자료·예상 질문 | "발표 15분용 자료와 예상 질문" | 슬라이드 + Q&A |
| 4 | 가격 제안서 | "가격 제안 부분만" | 가격 표 + 산출 근거(내부용) |
| 공통 | 일정·할 일 | "이번 주 마감 건 정리" | Deal별 할 일 목록 |
| 공통 | 트렌드 분석 | "올해 명절 선물 공고 경향" | 집계 기반 요약 |
| 공통 | 자유 질문 | 분류되지 않는 요청 | 근거 범위 안의 답변 + 가까운 작업 유형 제안 |

분류가 애매하면 후보 유형 2\~3개를 버튼으로 보여 주고 고르게 합니다. 같은 방식(작업 유형 레지스트리)을 B2C 대화와 셀러 센터, CS에도 그대로 써서 대화 라우터를 하나로 유지합니다.

## B2C·B2B 공통 CS

CS는 채널과 무관한 티켓 하나로 받습니다: 웹 문의창이든 이메일이든 나중의 메신저든 같은 티켓이 되고, AI가 1차 답변을 하되 확신이 낮거나 금전·법적 사안이면 운영자에게 넘깁니다.

**처리 흐름**

1. **접수** — 문의 채널, 고객 유형(고객·셀러·발주처·협력업체), 관련 주문·상품·Deal을 티켓에 연결합니다.
2. **분류** — 작업 유형 레지스트리로 문의 유형을 정합니다.
3. **AI 1차 답변** — FAQ·운영 정책·상품 정보만 근거로 답하고 출처를 남깁니다. 근거가 없으면 답하지 않고 이관합니다.
4. **이관** — 환불·교환, 개인정보, 법적 문의, 불만, 신뢰도 낮음은 운영자 대기열로. 답변 초안은 AI가 붙여 둡니다.
5. **종결·학습** — 운영자 답변 중 반복되는 것을 FAQ 후보로 올리고, 승인되면 지식베이스에 추가합니다.

| 고객 유형 | 주요 문의 | 판매 유형별 처리 |
| --- | --- | --- |
| B2C 고객 | 추천 이유, 레시피, 가격, 주문·배송, 반품 | 제휴(쿠팡) 상품 → 쿠팡 고객센터로 안내 · 입점 상품 → 셀러에게 티켓 전달 · 직판·구매대행 → commerce\_ai가 직접 처리 |
| 입점 셀러 | 입점 심사, 상세페이지 수정, 정산 | 셀러 센터 티켓, 운영자 처리 |
| B2B 발주처 | 제안 내용, 납품 일정, 견본 | Deal에 연결, 운영자 처리 (AI는 초안만) |
| 협력업체 | 견적 회신, 공급 일정 | Deal·업체 등록부에 연결 |

**운영 기준 (1인 운영 가정)**

- 응답 목표: 영업일 24시간 이내, 화면에 그대로 안내
- AI 자동 종결은 정보성 문의(레시피·사이트 사용법)만 허용
- 모든 티켓에 AI 답변 여부를 표시해, 고객이 사람 상담을 요청할 수 있게 함

직판 상품이 생기기 전까지 CS 물량은 대부분 정보성 문의일 것이므로, 1단계는 웹 문의창 + FAQ 봇 + 관리자 티켓함으로 충분합니다.

## UCP·구글 노출과 결제 연동

UCP 기반 구글 결제는 지금 한국 판매자가 참여할 수 없고, 참여 범위는 시점과 역할별로 다시 확인해야 합니다. 그래서 "구글에 보이는 것"과 "구글에서 결제되는 것"을 나눠, 앞쪽은 지금 시작하고 뒤쪽은 조건이 열릴 때 붙입니다.

**현재 조건 (2026-11 확인)**

- 구글의 UCP 기반 결제는 미국·캐나다·호주에서 판매 가능한 상품, 참여가 허용된 일부 판매자에게만 적용됩니다 ([Google Merchant Center 도움말](https://support.google.com/merchants/answer/16837055?hl=en)).
- 참여 신청서는 미국·캐나다·호주에서 출고하고 현지 은행 계좌가 있는 판매자를 대상으로 합니다 ([UCP 참여 신청서](https://support.google.com/merchants/contact/ucp_integration_interest?authuser=2)).
- 판매자·Merchant Center·결제대행사·결제 토큰의 정확한 요건은 구글 공식 문서와 계약으로 최종 확인합니다. 제3자 보도는 의사결정 근거로 쓰지 않습니다.
- 쿠팡 제휴 링크는 commerce\_ai가 판매자인 상품으로 표현하지 않습니다. 입점·구매대행도 주문·결제·판매 주체를 확인하기 전에는 UCP 결제 가능 상품으로 분류하지 않습니다.

**단계별 전략**

| 단계 | 내용 | 시작 조건 |
| --- | --- | --- |
| A. 검색 노출 | 트렌드 글·레시피·상품 페이지에 구조화 데이터(schema.org Recipe·Product·Article), 사이트맵, 빠른 로딩 | 지금 |
| B. 에이전트 노출 | UCP 프로필·카탈로그·원격 MCP의 인증, HTTPS, 데이터 권한, 판매 주체·출처 표시를 검증한 뒤 공개 결정. 2026-11-04 기준 UCP 어댑터는 기본 꺼짐·미연결 | 검증 후 결정 |
| C. 머천트 데이터 | Merchant Center 계정, 상품 피드(직판·입점 상품), 반품 정책 등록 | 사업자등록·통신판매업 신고 후 |
| D. 자체 결제 | 국내 PG 계약, 직판·구매대행 주문·결제·환불 | C 이후, 직판 상품 확보 시 |

A·B의 노출과 유입은 보장된 결과가 아니라 측정할 가설입니다. 게시·색인·에이전트 인용·전환을 나눠 측정합니다. E는 결제 수수료·환불 책임이 따르므로 직판 물량이 생긴 뒤 판단하는 것이 안전합니다.

## 카카오톡·네이버 톡톡 연계 검토

결론: **지금은 둘 다 연계하지 않는 것이 맞습니다.** 다만 직판 주문이 생기면 카카오톡 채널은 CS·주문 알림용으로 필요해질 가능성이 높으므로, CS 모듈을 채널 중립으로 만들어 나중에 어댑터만 붙이게 합니다.

| 항목 | 카카오톡 채널 | 네이버 톡톡 |
| --- | --- | --- |
| 연동 방식 | 채널 개설 + 챗봇(카카오 i 오픈빌더) 스킬 서버 연결 | 톡톡 파트너센터 계정 → 챗봇 API 신청, 웹훅·보내기 API ([공식 문서](https://github.com/navertalk/chatbot-api)) |
| 강점 | 국내 고객 접근성 최고, 주문·배송 알림(알림톡)에 사실상 표준 | 네이버 검색·스마트스토어 고객과 연결, 상담원 이관·네이버페이 버튼 확장 API ([핸드오버](https://github.com/navertalk/chatbot-api/blob/master/handover_v1.md), [Pay API](https://github.com/navertalk/chatbot-api/blob/master/pay_api_v1.md)) |
| 지금 쓰기 어려운 이유 | 알릴 주문이 없고, 상담 물량도 적음. 알림톡은 건당 비용과 사업자 정보 필요 | 스마트스토어를 운영하지 않음. 쇼핑커넥트도 네이버 안에서만 쓰므로 사이트 고객과 겹침이 적음 |
| 비용·부담 | 챗봇 응답 품질 관리, 채널 운영 시간 | 계정 검수, 챗봇 품질 관리 |
| 판단 | **보류 — 직판 시작 시 1순위로 재검토** | **보류 — 스마트스토어 개설 시에만 검토** |

**재검토 조건**

- 직판·구매대행 주문이 월 수십 건 이상 생겨 배송 알림이 필요할 때 → 카카오 채널 + 알림톡
- 웹 문의창 CS가 주당 처리 한계를 넘을 때 → 카카오 채널 상담(처음엔 사람 응대)
- 네이버 스마트스토어를 열 때 → 톡톡

설계상 준비할 것은 한 가지입니다: CS 티켓과 알림 발송을 `channel` 필드로 추상화해 두면, 메신저 연동은 나중에 어댑터 하나로 끝납니다.

## 부록 — 개발 근거와 경계

이 부록은 개발·검증용입니다. 본문의 결정을 바꾸지 않고, 구현 전에 지켜야 할 경계와 아직 채택되지 않은 설계 후보를 적습니다.

### A. 추천·비교 엔진 소유 경계

GPT 대조판에 따르면 비교 정체성 엔진(PM-1)은 `app/services/comparison/compare_identity_engine.py`, 스냅샷 엔진(PM-2)은 `app/services/comparison/compare_snapshot_engine.py`가 정식 경로이고, PM-2가 쓰는 `price_signal_engine`·`score_engine`은 추천 쪽 소유입니다. 이 경로와 완료 상태는 전달된 결과이며, 실제 저장소에서 다시 확인해야 합니다.

- 추천·가격·점수 설명은 상품·판매 제안의 식별과 출처, 가격 관측 시각, 점수 산식 버전, 후보 제외 사유, 최종 표시 순위를 구분합니다.
- KAMIS 공공 가격은 참조 자료이며 개별 판매 제안의 확정 가격이나 품질 검증이 아닙니다.
- 광고·제휴 배지와 일반 결과의 순위 결정은 별개 원칙으로 다룹니다.
- 해외 인기 지표와 배송 제공자 선택 점수는 기존 추천 엔진에 자동으로 합치지 않습니다.

### B. 해외 거래 데이터 계약 후보 (미채택)

기존 `Offer`에 바로 Pydantic 필드를 붙이지 않고, 판매 유형별 책임과 외부 참조를 보존하는 의미 계약을 먼저 정합니다. 가격·관세·배송·규제 값은 **값 + 통화/단위 + 산출 기준 + 출처 + 기준 시각 + 적용 국가/서비스 + 불확실성**으로 저장하고, 규제 상태는 참/거짓 대신 **확인 / 불충분 / 미확인 / 적용 제외**와 근거·유효기간을 둡니다. DDP 같은 인도조건은 계약 당사자·운송 상품·도착국 조건을 확인한 경우에만 표시하며, "수취인 추가 청구 없음"의 보증과 혼동하지 않습니다.

| 개념 | 최소 의미 | 소유·검증 경계 |
| --- | --- | --- |
| 판매 제안·채널 | 상품 후보, 판매 주체/계약 주체, 공개 채널, 표시 통화 | 판매 유형·셀러 검증은 별도 결정 |
| 출고·도착 범위 | 출고국, 도착국, 서비스 가능 국가, 금지 품목 | 카탈로그 필터와 실제 결제·운송 가능성을 분리 |
| 가격 견적 | 상품가·국제 운임·현지 배송·관세/세금·통관 수수료·반송 예비비 | 견적/확정/실비 구분, 납부 주체와 만료 시각 보존 |
| 규제 검토 | HS 분류 후보, 서류, 수입자, 당국/운송사 확인, 적용·예외 근거 | 품목·국가·시점별 검토. 코드가 자동 허가하지 않음 |
| 물리 단위 상관관계 | 첫 마일 단위 ↔ 외부 WMS·선적·포장·운송장 참조 | 발급자·근거·1:N/N:1·정정 이력 필수 |
| 이벤트 관측 | 원천 상태, 발생/기록 시각, 장소, 보고자, 확인 수준, 충돌 | 주문 완료·법적 책임으로 자동 승격 금지 |

### C. 해외배송 마지막 구간(라스트마일)과 증거 경계

해외 고객의 실제 인도나 한국 고객의 수령까지 추적하려면 첫 집하부터 최종 배달까지 외부 주체의 증거를 이어야 합니다. 내부 설계 결정(B4-A M7)은 추적 상태만으로 수령을 확정할 수 없다고 정했고, D10/D11은 첫 마일 참조와 외부 허브·WMS·운송장 참조를 출처를 밝혀 연결하는 방향만 승인했습니다. 통관·현지 운송·최종 수령의 운영 상태·연동·책임 정책은 아직 채택되지 않았습니다.

| 구간 | 확인할 근거 | 표시·처리 경계 |
| --- | --- | --- |
| 출고·첫 마일 → 허브 | 집하 단위, 제공자 인수, 허브 수령자 확인, 수량·예외 | 제공자 일방 보고와 허브 수령 승인을 구분. 법적 보관·소유권 판정 아님 |
| 포장·국제 운송 | 허브/WMS 참조, 분할·합포장, 선적·포장·운송장 매핑, 운송사 인수 | 임시 첫 마일 참조를 정식 송장·패키지 ID로 승격하지 않음 |
| 도착국 통관 | 도착·신고·보완요청·검사·보류·납부·반출 사건 | '통관 완료'와 '현지 배송사 인수'를 별도 상태로 표시 |
| 현지 배송 | 국제→현지 운송사 인계 근거, 현지 송장, 배송 시도·실패·보관·재배달 | 국제·현지 운송장은 다대다일 수 있음. 예상 도착일은 보장 아님 |
| 최종 인도 | 운송사 배송 보고, 수령자·대리수령 확인, 서명·사진·보관함 기록 | '배송 완료'는 출처 있는 관측, '수령 확인'은 추가 증거와 정책 판단 뒤 표시 |
| 예외·역물류 | 주소 오류, 통관 거부, 파손, 분실, 부분 배송, 반송·환불, 증거 정정 | 충돌·누락·미확인을 성공/실패로 덮지 않고 CS와 책임 주체에 이관 |

- 각 사건은 발급자·출처, 외부·내부 주문 참조, 단위 수량, 발생·기록 시각, 장소, 행위자, 증거 링크, 신선도, 충돌·정정 이력을 보존합니다.
- 한 주문이 여러 포장으로 나뉘거나 여러 집하 단위가 한 포장으로 합쳐질 수 있으므로, 주문 상태만으로 모든 포장의 수령을 판정하지 않습니다.
- 배송 증빙이 운송 상품이나 도착국에서 제공되지 않으면 미확인으로 남기고, 고객의 미수령 신고를 CS로 연결합니다.
- **운영 책임** — 직구 링크는 해외 판매처·운송사가 주문과 마지막 배송의 1차 담당이고, commerce\_ai는 안내와 자체 표시 오류를 처리합니다. 구매대행·직접판매는 계약상 주문·통관·배송·반품·응대 주체를 먼저 정합니다. 운송사 사건을 수집해도 법적 보관·소유권·배상·환불 책임을 추정하지 않습니다.
- 배송 제공자 평가(주장·능력·약속 SLA·관측 실적·고객 피드백)와 자동 선택·배정은 별도 연구 후보(B4-B)이며 아직 승인되지 않았습니다.

### D. 내부 결정 확인 항목
