## 2. 세 탭의 자료와 규칙
### 2-1. 급상승
- 자료: 급상승 리포트(`surge.public_view` — 서버 안에서 재사용, 홈은 `/api/home/rankings` 하나만 부름). 홈에는 **상위 6개 + '전체 보기'**(탭 '지금 뜨는 식품' 전체 화면은 전부): 순위 번호(우리 목록 순서), 키워드, **"검색 관심도 평소의 약 n배"**(네이버 데이터랩 검색어 트렌드 **상대 지수** — 약 한 달 전 평소 대비 배수, ⓘ에 계산 기준), 식품 검색어 n위 배지, 시작일. 계기(AI 추정)는 홈에선 생략(탭에서).
- 누르면 `it.ask` 로 대화 시작(지금 TrendsPage 와 같은 `PENDING_ASK` 흐름 → 홈에서는 바로 `onSend`).
- 기준 시각: `data_until` + "하루 한 번 갱신".

### 2-2. 카테고리
- 자료: **그날 식품 검색어 순위 파일**(`period.read_ranks`, 상위 100)을 **태그 규칙표**로 나눈 것. 번호 = 데이터랩 순위(그 카테고리 안 순서가 아니라 원래 순위를 그대로 표시 — "식품 검색어 12위").
- 태그 규칙표 `data/keyword_tags.csv` (열: tag, label, icon, pattern(정규식), lexicon(쉼표), ask_template). 시작 태그 8개 — 카카오의 '교환권·뷰티·식품·건강·리빙' 대신 **식품 하위**:
  `gift 선물` · `snack 간식/디저트` · `fruit 과일` · `seafood 수산` · `meat 정육/계란` · `health 건강식품`(표현 검사 통과 문구만) · `cook 요리/식재료` · `season 시즌`(김장·명절·수능·빼빼로 — 행사 달력 기준 **행사별 준비 기간**, 아래). 규칙은 `update_trend_examples.py` CATEGORIES 의 사전·정규식을 **파일로 빼서** 둘이 같은 표를 쓴다(리포트 연구의 '태그 규칙표'와 동일 파일 — 한 곳).
- **한 키워드에 태그 여러 개 허용**(GPT 검토: 선물·시즌이 앞이면 과일·수산이 가려짐) — 탭은 그 태그를 가진 키워드를 거르기만 하고 원래 순위는 보존. 어느 태그에도 안 들면 '그 밖' — 홈에는 안 보임. 태그 이름은 1차에 **'과일'·'요리/식재료'**로 두고, '제철' 은 계절 근거(행사 달력·제철 표)가 확인된 키워드에만 **배지**로. **시즌 태그는 행사 당일 주가 아니라 행사별 준비 기간**(행사 선행 곡선의 −28…행사 끝, 김장은 달력의 '김장 시즌' 창)으로.
- **늘 상위인 키워드 처리(사용자 지적 2026-11-20 11:14, GPT 2차 12:48 반영)**: 건기식·쌀·생수처럼 1년 내내 100위 안인 키워드가 카테고리 탭을 차지하지 않게, 행사 선행 곡선의 '유지형' 규칙을 가져옴. 키워드 상태 셋 —
  - `steady` **늘 인기** = 최근 90일 창에서 **관측일(**정상 파일** = 그날 순위 파일이 있고 완전성 검사 통과 — 500행·중복 없음·날짜 일치 — 인 날) ≥ 60 이고 그중 100위 안 비율 ≥ 80%**
  - `other` = 관측일 ≥ 60 인데 조건 미충족
  - `insufficient` **판단 자료 부족** = 관측일 < 60 (백필 전 상태 — 상승 가능성처럼 보이지 않게 따로 표시, "자료 n일")
  - 응답에 창 길이·관측일 수·100위 안 일수를 같이 실어(`window_days`·`observed_days`·`top100_days`) 자료 충실도를 보이게 함.
  - **'오르는 중'은 이 상태와 별개** — 7일 전 파일과 오늘 파일이 **둘 다 정상 파일(존재 + 완전성 검사 통과)일 때만** 순위 차로 판단(`change_7d` = 개선 계단 수). 7일 전 파일이 없으면 `no_compare`('비교 자료 없음', NEW 아님). 7일 전 정상 파일에 키워드가 없었으면 `entered`('상위 500위 진입' — 우리 파일은 500위까지이므로 '100위 진입'이라 쓰지 않음).
  - 기본 보기 = **'오르는 중'** = `(state ∈ {other, insufficient}) AND (change_7d > 0 OR change_kind = entered)` — 괄호 그대로 코드·테스트에 쓰고, `steady` 는 어떤 경우에도 '오르는 중'에 안 들어감. 순위순 → 접힌 줄 "늘 인기 n개"(steady) → 칩: 전체 / 오르는 중 / 늘 인기 / 자료 부족.
- 누르면 **"{kw} 추천해 줘"** 한 가지(GPT 검토: 고객이 고르지 않은 조건 — '가정용 2~3kg' — 을 끼워 넣지 않음). 조건은 대화에서 되묻기(기존 흐름). 누름은 **1회만 전송**(두 번 눌러도 중복 질문 없음).
- 기준 시각: 자료 기준일 = 순위 파일 날짜("순위 11/20 자료 · 네이버 식품 검색어"), 갱신 시각은 따로.

### 2-3. 트렌드 상품 (1차 이름 — 사용자 결정 2026-11-20 12:39)
- **이름**: 1차는 **'트렌드 상품'**(GPT 검토: 지금은 최신 승인 글에서 가져온 상품이지 AI 가 평가한 순위가 아님). 실제 AI 평가·근거가 붙을 때 'AI 추천상품'으로 바꿈 — 그때 '왜' 칸에 평가 근거(비교 기준·확인 시각)가 함께 있어야 함.
- 1차 자료: **승인된 트렌드 글의 상품**(`posts.published()` → `post.products`, 최신 승인순, 글당 1~2개, **홈에 6개 표시**(사용자 확인 11:14), 탭 전체 화면은 20개). 같은 상품이 여러 글에 있으면 **쿠팡 상품 번호(productId)로 중복 제거**(가장 최근 글 하나만). 카드: 사진·'쿠팡'·상품명·가격(확인 시각)·로켓/무료배송·**왜**(글 제목 한 줄, "트렌드 글 기준")·링크 `/trends/{글}/go/{n}`(클릭 기록). 위에 고지 문구.
- **오래 남는 상품의 표기(사용자 결정 11:14 '지속 인기 상품' → GPT 2차 12:48 반영으로 배지 뜻을 근거대로 나눔)**: 키워드가 오래 상위권이라는 사실은 그 상품의 인기를 뜻하지 않고, 글 두 편에 든 것은 운영자의 반복 선정 기록이라서 '지속 인기 상품'이라 부르지 않음. 대신 근거별 배지 둘 —
  | 근거 | 배지 | 정의(API·카드·테스트 공통) |
  |---|---|---|
  | 관련 키워드가 꾸준히 상위권 | **관련 키워드 꾸준한 관심** | 상품의 키워드가 최근 30일 창에서 **관측일 ≥ 20 이고 그중 100위 안 비율 ≥ 80%** — 화면·문서 설명은 **'최근 30일 창에서 관측된 날짜 중 80% 이상 100위 안'** 한 가지로 통일('30일 넘게'·'24일 이상' 같은 말은 쓰지 않음 — 관측일 20일이면 16일로도 충족) |
  | 같은 상품을 여러 글에서 선정 | **여러 트렌드 글에서 소개** | 같은 productId 가 승인 글 **2편 이상**(간격 조건 없음, 편 수 표시) |
  | 상품 자체의 구매·관심 실적 | (없음) | 현재 자료로 확인 불가 — 지어내지 않음 |
  - **배치 기준(GPT 3차 13:00 반영 — 두 묶음)**: 상품 목록은 **묶음 둘**로 나눠 만든다 — ① `recent` **최근 소개**(승인 글 최신순, 글당 1~2개) ② `steady` **관련 키워드 꾸준한 관심**(배지 `keyword_steady` 상품, 최신 승인 글 순). 같은 productId 는 **두 묶음 사이에서도 한 번만**(steady 에 들면 recent 에서 뺌), 각 묶음 **내부 정렬은 고정**(승인 시각 내림차순 → productId 오름차순으로 동률 해소). 홈 = recent 앞 4 + steady 앞 2(steady 가 2개 미만이면 recent 로 채움, 그 반대는 없음), 전체 화면 = recent 앞 16 + steady 앞 4. 화면은 두 묶음을 소제목으로 구분하고('최근 소개' / '관련 키워드 꾸준한 관심'), 응답 `placement_note` 에 같은 문구. '최신 글 순'만으로 설명하지 않음.
  - **홈·전체 화면 일치 테스트는 묶음별로**: `home.recent == full.recent[:4]`, `home.steady == full.steady[:2]`(채움이 일어난 경우 recent 는 `full.recent[:4+채운 수]`). 전체 배열 앞 6개 = 홈 이라는 조건은 **쓰지 않음**(4+2 와 16+4 는 섞으면 일치하지 않음).
  - **가격 갱신은 홈 응답에서 하지 않음**(GPT 2차: '새 수집 없음' 원칙·외부 API 지연이 홈 로딩에 번짐). 홈은 **저장된 자료만** 읽고, 30일 넘은 가격은 숨김("가격은 판매처에서 확인"). 갱신은 **홈 1차의 필수 조건이 아닌 후속 작업(§5 2-b)** — 관리자 '상품 가격 갱신' 실행 또는 별도 주기 작업(예: 매일 10:10, 순위 갱신 뒤)으로 `posts.refresh_products` — 재검색 결과가 **같은 productId·같은 옵션**일 때만 기존 가격·배지·확인 시각을 바꾸고, 다르면 바꾸지 않고 '확인 필요' 표시.
- 2차(예측 모델 창이 끝난 뒤 추가): **행사 D-day 묶음**(`forecast/events` 예보 재료 중 쿠팡 상품 후보가 있는 키워드 → "수능 D-6 · 수능선물") · **가격 레이어 '지금' 품목**(`forecast/prices.summary` verdict=지금 → "지금이 싼 구간 · 52주 하위 20%" + 국내 상품). 이때도 상품 순서는 추천 점수가 아니라 **행사 가까운 순·판정 순**임을 문구로.
- 뒤에 'AI 추천상품'으로 바꿔도 **가격·품질 단정 없음**, 근거(글·순위·시세)와 확인 시각을 카드에 같이 — 1단계 근거 표시 원칙.

## 3. API — `GET /api/home/rankings?view=home|full` (하나로, 캐시 5분)
`view=home`(기본) = 급상승 6 · 카테고리별 6 · 상품 6, `view=full` = 급상승 전부(계기·단서 포함) · 카테고리 100위 전부 · 상품 16+4 — **같은 선정 규칙**(태그·상태·배치)을 쓰고 개수만 다름(테스트로 고정: 급상승·카테고리는 full 앞 n개 = home, 상품은 **묶음별** 앞부분 일치 §2-3).

- 기존 함수 재사용: `surge.public_view`, `period.rank_files/read_ranks`, `cal.upcoming`, `posts.published()`·`render` 의 가격 숨김 규칙(`price_claims` 30일). 새로 만드는 것은 태그 규칙표 읽기(`app/services/trends/tags.py`)와 이 라우트뿐. **홈은 이 API 하나만 부른다**(§2 의 '기존 API'는 서버 안 재사용을 뜻함).
- **부분 실패**: 세 영역이 각자 `status·기준일·갱신 시각·items` 를 가짐 — 급상승 리포트가 없어도 카테고리·상품은 나옴. 오래된 자료는 `stale` + 마지막 기준일을 그대로 보여 줌(지어내지 않음).
- **기준 시각 분리**(GPT 검토): ① 자료 기준일(순위 파일 날짜·급상승 data_until) ② 서버 갱신 시각(generated_at) ③ 가격 확인 시각(상품마다) — 셋을 섞어 "10:00 기준" 하나로 쓰지 않음. 화면 문구: "순위 11/20 자료 · 11:05 갱신", 카드엔 "가격 11/18 확인".
- **가격 '30일 뒤 숨김'의 뜻**: 기존 구현 규칙(`price_claims`)의 재사용일 뿐 30일 동안 '현재 가격'이라는 뜻이 아님 — 카드엔 항상 **'확인 당시 가격 + 확인일'**. 실제 표시 가능 기간은 쿠팡 파트너스 이용 조건에 맞춰 확인(결정 대기). 품절·로켓/무료배송 배지도 같은 확인 시점을 붙이고, 가격과 같은 만료 규칙(30일, 재검색으로 갱신)을 적용.
- **공개 응답 허용 목록**(기존 surge 공개 규칙의 뜻을 명확히): 내보내는 것 = 키워드 자체·순위·배수·시작일·태그·ask 문장·승인 글 제목/링크·상품 카드 필드. 내보내지 않는 것 = 수집에 쓴 **검색 질의문·API 이름·호출 기록·내부 파일 경로·미승인 글·운영자 메모**.
- 정책 검사(테스트로 고정): 미승인·철회(withdrawn) 글 상품 0, 30일 지난 가격 숫자 0, **홈 응답이 외부 호출을 하지 않음**(쿠팡·네이버 호출 0 — 저장 자료만), 고지 문구가 상품 앞, 링크는 `/go` 경유만, 응답에 내부 질의문·API 이름·파일 경로 없음(위 허용 목록), **원래 식품 순위 보존**(태그로 걸러도 rank 값·순서 불변), **태그 중복 허용**(한 키워드가 두 탭에 나옴), **과거 자료 표시**(stale 이면 마지막 기준일), **같은 상품 중복 제거**, 관측일 < 60 이면 `insufficient`(steady·other 아님), 7일 전 파일 없으면 `no_compare`(NEW 아님), 배치 4+2 규칙(묶음 둘, 묶음 사이 중복 0, 묶음 내부 정렬 고정, steady 부족 시 recent 로 채움), `view=full` 묶음별 앞부분 = `view=home`, '오르는 중' 집합에 steady 0개, 불완전 파일(행 수 부족·중복)은 관측일에서 제외, 가격 갱신은 같은 productId·옵션일 때만(관리자/주기 작업 테스트), 키워드 클릭 **1회만 전송**(프런트 테스트).

## 4. 화면 — `frontend/src/components/HomeRankings.tsx`
- 자리: 홈 머리글·입력창·예시 질문 4개 **아래**, '오늘의 트렌드' 글 줄 **위**. 섹션 제목 "지금 순위" + 기준 시각 + ⓘ(설명 팝오버: 순위는 네이버 식품 검색어, 상품은 승인 글 기준, 제휴 수수료는 순위에 영향 없음).
- 알약 탭 3개 — **급상승 · 카테고리 · 트렌드 상품**(이름은 §6) (카카오처럼 가운데 정렬, 선택 탭 흰 배경). 카테고리 탭 안에는 아이콘 칩 가로 스크롤(전체·선물·간식·과일·수산·정육/계란·건강·요리/식재료·시즌) + 둘째 줄 작은 칩 '오르는 중(기본) / 늘 인기 / 전체'. 키워드 줄 끝에 ↑n·↓n·NEW, 계절 근거가 있으면 '제철' 배지.
- **탭 '지금 뜨는 식품' 확장(사용자 결정 11:14 — 권장안 채택)**: 홈은 요약(급상승 6 · 카테고리별 6 · 상품 6, 각 '전체 보기'), 탭 '지금 뜨는 식품'은 같은 세 알약 탭의 **전체 화면**(급상승 전부 + 계기·단서, 카테고리 100위 전부, 상품 20개). 지금 TrendsPage 의 카드(배수·단서·계기·트렌드 글 읽기)는 급상승 탭 안으로 들어감.
- **홈 밀도**(GPT 검토): 입력창 아래 긴 목록이 대화 시작을 밀지 않게 **각 탭 6개 + '전체 보기'**(탭 '지금 뜨는 식품'으로). 급상승·카테고리: 번호 + 키워드 + 배지 한 줄 목록(모바일 1열). 상품: 2열 카드(사진 1:1, 판매자, 상품명 2줄, 확인 당시 가격 + 확인일, 배지(확인일 같이), '왜' 한 줄).
- 누르기: 키워드 → `onSend(ask)`(대화 시작) · 상품 → 판매처(새 창, `/go`) + 작은 '대화로 묻기' 버튼. '장바구니'·'주문' 문구 0.
- **시즌 한 줄(사용자 제안 12:48 → GPT 3차 13:00 로 범위 조정, 넣을지는 보류)**: '지금 순위' 제목 옆 한 줄 — 행사 달력 `upcoming()` 기반 **행사 이름 + D-day 칩**("김장 시즌 · 수능 D-6") **+ 행사 날짜에만 근거한 일반 안내 문장**("설 선물을 미리 둘러보세요", "김장 재료를 둘러보세요")까지 허용. 안내 문장은 §8 의 **허용 표현표**에서만 고르고(행사당 1~2문장, 달력 파일에 둠), 새 수집 없음. **검증이 필요한 주장**("지금이 가장 싸요", "2주 전이 최적", "작년보다 n% 올랐어요")은 예측 모델·가격 레이어 백테스트 뒤 **사실 서술형**으로만(§8). 알림톡 심사 기준을 홈 문구에 그대로 적용하지 않음. 홈이 복잡해지면 칩만 남기거나 생략.
- 빈 상태: "아직 오늘 순위가 없어요(매일 10시 갱신)" / 상품 없음 → 탭 숨김.
- 화면 시험(2단계 상세 방식) 시나리오 추가: 홈 → 지금 순위 → 탭 셋 전환 → 카테고리 칩 → 키워드 누르면 대화 시작 → 상품 카드 고지 문구가 첫 링크보다 앞 → 링크 `/trends/…/go/…`.
