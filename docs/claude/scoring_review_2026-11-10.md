# 추천 점수 재검토 — 연구가 필요한가 (2026-11-10)

계기: 평점·리뷰(2026-11-02 결정)와 플랫폼 이름 점수(2026-11-10 결정, 보류)를 DB 뷰 점수에서 빼자, 점수의 바탕이 거의 남지 않음.
근거: `sql/reference/*.current.sql`(Mac DB 덤프), `app/services/recommendation/scoring.py`·`provider.py`·`trust_adapter.py`, `app/services/platform_score_engine.py`.

## 결론
**연구가 필요합니다. 다만 가중치 조정이 아니라 "쓸 수 있는 근거부터 다시 세는" 연구입니다.** 1단계(근거 표시)는 막지 않고, 별도 흐름으로 2단계 전에 결론을 냅니다.

## 1. DB 경로(채팅 추천의 예비 경로) — 남는 것이 거의 없음
최종 점수 = `trust_first_score` + 클릭 가산(0~15) + CTR 가산(0~15) + 순위 대비 CTR(−5~10) + 가격 하락(0~15) + CTR 피드백 가산, 100 상한.

| 요소 | 상태 | 판정 |
|---|---|---|
| 평점·리뷰 (trust 60%) | 페이지 보강 값, 출처 미검증 | 제외 (11-02) |
| 플랫폼 이름 (trust 15%) | 컬리 80·우체국 75·네이버·쿠팡 70 | 제외·보류 (11-10) |
| 고당도 (trust 25%) | `is_high_brix` 참/거짓 하나 — 대부분 판매자 상품명 표기 | 판매자 주장, 둘 중 하나 값 |
| 클릭·CTR 가산 | 자체 클릭·노출 기록 | 양·품질 미확인 (가족 클릭 금지 규칙, 시험 클릭 섞임 가능) |
| 가격 하락 가산 | 가격 스냅샷 마지막 수집 2026-07-16 | 4개월 전 변화 |
| 가격·kg당 가격·할인 (`recommendation_score`) | 계산은 되지만 | **최종 점수에 안 쓰임** — `COALESCE(trust_first_score, recommendation_score)`에서 trust_first가 항상 있음 |

평점·리뷰·플랫폼을 상수로 바꾸면 **기본 점수 `trust_first_score`**는 두 값(고당도 53.25 / 아니면 44.5)뿐입니다 — 최종 점수가 아니라 기본 점수입니다. 이 기본 점수에서 상품을 구분하는 것은 `is_high_brix` 하나이고, 최종 순위에는 클릭·CTR 가산, 가격 하락 가산, 모드·상품 boost, (session_id가 있으면) 개인화 보정이 더해집니다. 가격 자체는 일반 모드 순위에 들어가지 않고, 가격 모드만 `main.py`에서 100g당 가격으로 다시 정렬합니다(100g당 가격은 35%가 없고 11%는 상품명 중량 추정).

→ 이 뷰 점수는 고쳐 쓸 대상이 아니라 **역할을 다시 정할 대상**입니다.

## 2. 주 경로(canonical pipeline) — 구조는 맞음, 실제 근거는 미확인
- 쿠팡 파트너스 API를 실시간 호출(`app/services/market/collector.py`), 네이버 쇼핑 API는 11-04 종료
- 설계가 이미 "근거가 없으면 점수도 가중치도 없음": `build_effective_weights`가 있는 근거만으로 가중치를 다시 나눔
- 평점·리뷰로 신뢰 점수를 만들지 않음(`trust_adapter`). `platform_score_engine`(쿠팡 72·네이버 68)은 앱 코드에서 쓰이지 않음(테스트만)
- **모름**: 실시간 쿠팡 상품에 실제로 어떤 근거(quality·price·trust·popularity·market·identity)가 채워지는가, fallback이 얼마나 자주 일어나는가. "가격 + 쿠팡 검색 순서가 사실상의 순위"는 **점검할 가설**이지 결론이 아님

## 3. 연구 범위 (제안)
| # | 질문 | 방법 | 산출 |
|---|---|---|---|
| R0 | fallback 발생률 | `recommendation_path` 기록(canonical_provider / db_fallback)으로 집계 | 경로별 비율 |
| R1 | 근거 목록: 신호마다 출처·검증 상태·신선도·채워진 비율 | DB 경로 — 읽기 전용 집계(`is_high_brix` 비율, 클릭·노출 기록 양과 기간, 가격 신선도). 주 경로 — 쿠팡 API를 **제한된 횟수**로 표본 호출해 구성요소별 **값이 채워진 비율**과 **실제 순위 계산에 쓰인 비율**(effective weight > 0)을 나눠 기록 | 근거 표 (경로 × 신호) |
| R2 | 모드별로 정직하게 말할 수 있는 것 | R1 표로 판정: 예) 검증된 신뢰 근거가 없으면 '신뢰' 모드는 이름·설명을 바꾸거나 숨김 | 모드별 허용 근거·화면 문구 |
| R3 | DB 경로의 역할 | ① 뷰 점수 폐기, DB 후보도 canonical 점수기로 계산(점수 체계 하나) ② 단순·투명한 정렬(관련도 → 비교 가능한 100g당 가격 → 확인 시각) ③ 예비 경로 자체 폐지 — 비교 | 결정안 |
| R4 | 순위를 무엇으로 평가하나 | 지금은 사용자 지표가 없음 → 고정 질의 세트 + 사람이 판정한 "좋은 후보" 목록으로 오프라인 평가 | 평가 세트·기준 |

원칙(로드맵 고정 원칙 그대로): 페이지 스크래핑 없음, 제휴 여부·플랫폼 이름으로 가점 없음, 근거 없는 품질·가격 단정 없음, 모든 가격에 확인 시각.

## 4. 로드맵과의 관계
- **1단계는 진행**: 새 산식이 아니라 "지금 점수에 무엇이 들어가고 빠졌는지"를 보여 주는 내부 화면. 이 연구의 R1 자료가 그대로 화면 근거가 됨
- 1단계의 '순위 불변' 기준점 = **실제로 반영한 보정이 모두 끝난 직후**의 결과. 비교는 세 지점으로 남김: ① 변경 전 → ② 뷰 보정(평점·리뷰·플랫폼) 후 → ③ 가격 결합 URL 한정 후. 일반 모드와 가격 모드는 따로 봄. 100g당 가격 계산·정렬 자격을 바꾸면 ④로 별도 비교점
- 연구 결론(R3)은 **2단계 전**에 결정. 점수·순위를 실제로 바꾸는 작업은 별도 단계로 다시 전후 비교
