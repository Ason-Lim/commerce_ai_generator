# B2B·레시피 AI 비교와 레시피 재편집·점수 제안 (2026-11-11)

요청: ① 공공 레시피는 후보군으로 빼고 GPT·Claude 벤치마킹, 레시피 이미지는 gpt-image ② B2B 제안서 1차·2차 모델과 DeepSeek 의 제안서·공고 분석 능력
③ 카페·블로그·유튜브 레시피 재편집 방향 ④ 레시피 추천 점수. **결정은 사용자가 분석을 보고 한다** — 아래는 측정과 제안.
결과 화면(아티팩트): "B2B·레시피 AI 블라인드 비교" — 모델 이름을 가리고 고른 뒤 공개.

## 지금 B2B 에서 AI 가 하는 일 (코드 확인)
- **공고 분석** (`app/admin/b2b/request_parser.py`): 규칙 추출이 먼저, 규칙이 못 찾은 칸만 LLM(LLM_PROVIDER=deepseek)이 채우고 "(LLM 추출 — 원문 대조 필요)" 표시.
- **제안서** (`proposal.py`): 문장 대부분이 **코드 템플릿**. AI 는 '1. 제안 요약' 문장 다듬기만 (polish, 새 숫자가 생기면 폐기 → Claude 가 의미 바뀐 줄 되돌림).
- **디자인**: docx·pptx·hwpx 는 코드가 그린다 (proposal_export·proposal_deck). 모델의 '디자인 역량'은 지금 결과물에 영향이 없다.
→ 모델을 바꾸는 효과가 큰 곳은 '공고 분석'과, 앞으로 AI 가 쓰게 할 '제안서 본문'이다.

## 측정 2 — 제안서 본문 (공고 3건 × 6모델)
`scripts/b2b_llm_compare.py proposal` — 정답 조건 + 회사 정보(빈칸) + 후보 상품(관측가)을 주고 사업 이해·전략·일정·운영·품질·위험·차별화·확인 사항을 쓰게 함.
- 자동 검사: **지어낸 숫자·실적·인증·수상은 여섯 모델 모두 0건** (걸린 낱말은 '로그인 인증', '[확인 필요: 인증]' 같은 정상 문맥). 공고 요건(인원·단가·VAT·배송·교환·구축·하한·정산) 누락 0.
  관측가 52,000원 감귤을 55,000원 하한 충족으로 단정한 모델 없음. 세 공고의 핵심 위험(VAT 충돌·2개 선택 시 합산가)도 모두 짚었다.
- **DeepSeek 에서 한자 섞임**: "감점风险" (중국어 '위험'). 고객에게 나가는 문서에서는 치명적 — 어느 모델을 쓰든 한자·외국 문자 검사가 필요
  (Claude 웹 검색 답에서도 "要즘" 1건).
- 비용 (제안서 1건): DeepSeek Flash 약 $0.005 · GPT-6.1 Sol $0.025 · DeepSeek Pro $0.03 · Claude Sonnet $0.053 · Claude Opus $0.078 · GPT-6 Astra $0.125.
  시간: Flash 25초 · Claude 33~35초 · GPT 41~44초 · DeepSeek Pro 77초.
- 글의 질(깊이·설득력)은 자동 검사로 갈리지 않는다 → 블라인드 비교 화면에서 사람이 고른다.

### B2B 모델 선택 (결정 대기 — 사용자)
- 공고 분석: 정답률은 모두 높고 차이가 작다 (DeepSeek Flash 100 vs GPT 104). 수익 사업이라 놓치면 비싼 일이므로 1차 GPT-6.1 Sol(정답·비용 균형)
  또는 Claude, 2차는 다른 회사 모델이 같은 공고를 다시 추출해 **값이 다른 칸만 사람에게** 보여 주는 방식이 비용 대비 효과가 크다 (건당 몇 센트).
- 제안서 본문: 블라인드 결과를 보고 1차를 정한다. 2차 교차 검증은 1차와 **다른 회사** 모델 (Claude↔GPT). 건당 비용은 모두 $0.2 미만이라 비용보다 품질로 고른다.
- 어느 쪽이든 붙일 검사: 새 숫자, 실적·인증 주장, 한자·외국 문자, 요건 누락, 관측가로 조건 충족 단정 — 걸리면 그 줄을 되돌리거나 사람 확인.
- 지금 코드에서 AI 가 본문을 쓰게 하려면 proposal.build 를 '확인된 사실 → AI 본문 → 검사 → 교차 검증 → 사람 확정'으로 바꾸는 작업이 필요 (별도).

### GPT·Claude 는 레시피를 어떻게 추천하나 (웹 검색을 켠 API, 3문항)
- 두 모델 모두 **여러 블로그·사이트·유튜브를 읽고 자기 말로 다시 쓴 레시피**를 주고 출처 링크를 단다 (GPT 3개, Claude 5~6개).
  "인기 샌드위치"는 에그마요·BLT·햄치즈 등 여러 개를 골라 주고, "굴국밥 2인분"은 링크 없이 일반 지식으로 쓴다.
- 즉 사용자가 원하는 '재편집'이 이들의 기본 방식이다. 우리 차별점은 이 위에 인분 계산·보유 재료·장보기 연결과 검사(재료·도구·단계 일치, 안전)를 얹는 것.

## 제안 1 — 공공 레시피를 후보군으로 (요청 반영)
한 요청에 후보를 여러 출처에서 모으고 점수로 고른다. 공공 레시피는 그중 하나.
- 후보 출처: ① 공공 레시피(식품안전나라·농사로 — 원문 있음) ② **재편집 레시피**(아래) ③ AI 레시피(출처 없이 일반 지식) ④ 외부 링크(블로그·카페·유튜브 — 바로가기만)
- 이미지: 사진 이용 조건이 확인된 출처(식품안전나라)만 원본, 나머지는 모두 gpt-image (gpt-image-2.5-flare, "AI 생성 예시 이미지" 표시).

## 제안 2 — 카페·블로그·유튜브 레시피 재편집
원칙: 남의 글·사진을 복사하지 않는다 (페이지 스크래핑 금지 원칙 유지). 재료 목록·조리 순서 같은 '방법'을 여러 출처에서 모아 우리 말로 다시 쓰고, 출처는 링크로 밝힌다.
| 방식 | 어떻게 | 장점 | 주의 |
|---|---|---|---|
| A. 검색형 AI 재편집 (추천) | Claude·GPT 의 웹 검색 도구가 페이지를 읽고 재구성 + 출처 링크 → 우리 검사(재료·단계 일치, 안전, 사람 이름 금지) → 저장 | 우리 서버가 페이지를 긁지 않음, 출처 자동, 지금 바로 가능 | 검색 품질은 모델에 따름, 건당 수 센트, 저작권 해석은 법률 확인 필요 |
| B. 유튜브 설명란 | YouTube Data API 의 영상 설명(재료·순서를 적어 둔 경우가 많음) → AI 재구성 + 영상 링크 | 공식 API, 인기 신호(조회수·날짜)도 함께 | 설명란이 빈 영상 많음, 자막은 Data API 로 못 받음 |
| C. 네이버 검색 API 요약 | 제목·요약(짧은 미리보기)만 → 요리 이름·인기 신호로만 사용 | 이미 연결됨 | 본문이 없어 레시피 재구성 불가 |
- 화면: "여러 레시피를 참고해 다시 정리 · 출처 3곳" + 출처 링크, 분량은 'AI 정리'로 표시, 사진은 AI 이미지.
- 여러 출처가 서로 맞는 내용(공통 재료·순서)만 쓰고, 출처마다 다른 값(분량·시간)은 범위나 '취향껏'으로 — 한 출처의 고유한 비법을 그대로 옮기지 않는다.

## 제안 3 — 레시피 추천 점수 (초안)
상품 점수와 같은 원칙: 근거가 없는 항목은 빼고 남은 항목으로 비중을 다시 나눈다, 제휴 여부는 넣지 않는다, 클릭·저장은 조건이 갖춰질 때까지 넣지 않는다(11-10 결정과 같음), 화면에 이유를 보여 준다.
| 항목 | 비중 | 무엇으로 |
|---|---|---|
| 요청 일치 | 30 | 요리 이름 일치, 인분·시간·도구·조리 방식·피할 재료 조건 |
| 신뢰도 | 25 | 출처 종류(공공 원문 > 여러 출처가 일치하는 재편집 > 단일 출처 > AI 단독), 검사 통과(재료·도구·단계·팁 일치, 안전) |
| 지금 관심 | 15 | 외부 신호만: 유튜브 조회수·게시일(API), 블로그·뉴스 언급 수, 데이터랩 검색량 추세 — '기사에 유행 언급'과 '실제 관심 증가'를 구분 표시 |
| 만들기 쉬움 | 10 | 단계 수, 조리 시간, 재료 수, 특수 도구 |
| 장보기 연결 | 10 | 보유 재료 활용 비율, 부족한 재료가 상품으로 연결되는 비율 |
| 제철 | 5 | 제철 재료 사용 (확인된 사실·저장된 식품 지식) |
| 보기 좋음 | 5 | 원본 사진 또는 AI 이미지 유무 |
- 검증 방법: 고정 요청 30개 + 사람이 고른 '좋은 레시피' 목록으로 오프라인 평가 → 점수 바꿀 때마다 전후 비교 (상품 순위와 같은 방식).

### 비용·이익 구조 (app/admin/b2b/costing.py — 적용)
- 항목: 상품 매입 · 포장 · **물류창고(입고·보관·피킹·출고)** · **택배** · **교환·반품 예비** · 운영·CS · 폐쇄몰 구축 배분 · **일반관리비**(금액 또는 공급가액 %) · 기타 → **1인 이익(이윤)·이익률·총 이익**.
- VAT 포함 예산은 ÷1.1 한 공급가액 기준으로 계산 (예전에는 VAT 를 빼지 않아 이익이 약 9% 부풀 수 있었음).
- 근거를 항목마다: 견적·계약(확인) / 가정 / 입력값 → 전부 확인이면 '확정', 아니면 '추정', 빈 항목이 있으면 '산출 불가'.
- **목표 이익률 → 최대 매입가** (소싱 기준). 예: 55,000원(VAT 포함)·목표 10%·창고 700·택배 3,500(가정) … → 최대 매입가 34,200원.
- B2B 콘솔: "매입가 32000(견적) 포장 1000 창고 700(가정) 택배 3500(가정) 반품 300 운영 800 기타 0 관리비 5% 이윤 10% 구축비 200만원으로 비용 계산".
- 제안서: 내부 부록에 이익·이익률·총 이익·최대 매입가, 제출본 '가격 제안'에는 단가 구성 항목(금액은 견적 전 [확인 필요]) — 내부 이익률은 넣지 않음.

### 제안서 지시문 v2 (C+B) — `scripts/b2b_llm_compare.py proposal2`
가격 근거 3단 구분(관측 소매가·온라인 최저가 검증·확정 공급단가), 관측가로 '충족' 단정 금지, 온라인가 > 예산은 모순 아님, 외부 가격 통제 표현 금지,
운영 구체 항목(명부 계정·중복 차단·확보 수량·쏠림·검수·기한 알림·정산 증빙·개인정보), 예산=상한, 단가 구성(이윤·관리비·택배·창고 포함), 마감 일시.
→ 다섯 모델 모두 규칙을 지켰다 (충족 단정 0, 이익률 숫자 0, 한자 0, 단가 구성 9~11항목). **모델보다 지시문이 품질을 더 크게 바꿨다.**
비용(N1 1건): DeepSeek Flash $0.005 · GPT Sol $0.04 · Claude Sonnet $0.08 · Claude Opus $0.13 · GPT Astra $0.22.

### PPT 제작 비교 — `scripts/b2b_ppt_compare.py`
같은 사실로 각 모델이 python-pptx 코드를 쓰고, 격리된 곳에서 실행 → LibreOffice 로 이미지 (블라인드 화면 'PPT 블라인드').
- 다섯 모델 모두 12장, 표지·목차·핵심 숫자 카드·표·흐름도·[확인 필요] 표시까지 갖춘 발표 자료를 만들었다.
- DeepSeek Flash: 첫 코드가 python-pptx 1.0 에 없는 기능을 써서 실행 오류 → 오류를 알려 주고 한 번 고쳐 성공. 글자가 가장 작고 빽빽함.
- Claude Opus: 흐름도·정산 공식 도식·마무리 장 등 발표 흐름이 가장 좋음 (단 응답 시간 때문에 생각 강도 low 로 실행).
- GPT Sol·Astra: 가격 근거를 가장 조심스럽게 씀, 일부 장에서 상자와 글이 겹침.
- Claude Sonnet·Opus·DeepSeek: 관측가만으로 '충족' 표시를 한 장이 있음 → v2 지시문 규칙을 PPT 지시문에도 넣어야 함.
- 주의: Claude 5.5 는 기본으로 깊게 생각하며 출력 상한을 거기에 쓴다 (16,000 중 13,935) → 긴 출력은 생각 강도(output_config.effort)를 정해야 함.
- 지금 서비스의 PPT 는 코드 템플릿(proposal_export·proposal_deck)으로 만든다. AI 가 발표 자료를 직접 설계하게 할지는 별도 결정.

### 아직 확인된 사실이 없는 것 (지어내지 않음)
협력 물류창고·택배사, 폐쇄몰 플랫폼, CS 체계, 실적·인증 → 제안서는 [확인 필요]로 남는다. 택배·창고비는 '가정'으로 넣어 이익을 '추정'까지만 계산.

### 제안 — 공고 맞춤 폐쇄몰 데모
공고마다 후보 상품으로 실제 동작하는 폐쇄몰 데모(로그인→1인 1개 선택→배송지→주문 확인→교환 신청)를 미리 만들고, 제안서·PPT 에 화면과 데모 링크를 넣는다.
commerce_ai 의 기존 화면 기술(React)로 '/mall/{공고}' 를 만들 수 있다. 협력 물류·택배가 정해지면 출고·송장 연동을 붙인다. (결정 대기)

### 유튜브 조회수 (레시피 점수 '지금 관심')
YouTube Data API `videos.list part=statistics` 로 조회수·좋아요·댓글 수를 받을 수 있다 (확인: 굴국밥 영상 5개 — 5,426~797,063회).
search 는 호출당 할당량 100, videos.list 는 50개 묶음 1 — 검색 결과 영상의 통계를 한 번에 붙이면 된다.
점수에는 조회수 그대로보다 '게시 후 일수로 나눈 하루 평균 조회수'와 좋아요 비율을 쓰고(오래된 영상 편향 줄임), 로그 척도로 상한을 둔다.
